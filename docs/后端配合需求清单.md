## 一、P0 阻塞：服务当前不可用

联调在 2026-08-26 晚间中断。故障是**逐步恶化**的，分三个阶段：

| 北京时间 | 现象 | 证据 |
| --- | --- | --- |
| 22:19–22:21 | 全部正常 | 17 个 GET + 12 个写接口全部按文档返回，含 429/400/401 错误分支 |
| 22:38–22:43 | `/health` 正常，业务接口全挂 | `POST /auth/login` 稳定卡满 **10 秒**后 500，网关头 `x-envoy-upstream-service-time: 10002`；偶发 `ECONNRESET` |
| 22:46 之后 | 整个服务不可达 | `/health` 也超时，随后 `connect ECONNREFUSED 101.126.38.12:443` |

### 关键线索：中间阶段 `/health` 是好的，业务接口是坏的

22:38–22:43 这段时间的表现很有指向性：

```
GET  /health        200   耗时  93ms   上游  0ms   {"status":"ok",...}
POST /auth/login    500   耗时 10117ms 上游 10002ms {"code":500,"message":"服务器内部错误"}
GET  /wallet        401   耗时 277ms   上游  1ms   {"code":401,"message":"缺少访问令牌"}
```

- `/health` 和 JWT 守卫都是**纯内存逻辑**，毫秒级返回 → Node 进程活着，事件循环没堵。
- `/auth/login` 是**第一个碰数据库的接口**（按 unionid/openid 查用户、没有就建号），
  卡的时长又恰好是 10000ms 这个整数 → 高度怀疑是 **PostgreSQL 或 Redis 连接超时**，
  连接池拿不到连接，等到 `connectionTimeoutMillis` 才放弃。

### 请求后端做三件事

1. **恢复服务**，并确认根因是连接池耗尽、数据库实例被回收，还是 DevBox 休眠。
2. **给 `/health` 加依赖探活**。现在它只回一个静态对象，
   数据库全挂的时候它照样 200，前端和运维都会被它骗过去。建议改成：

   ```json
   { "status": "ok", "service": "warmpet-api", "time": "...",
     "deps": { "db": "ok", "redis": "ok" } }
   ```

   任一依赖不通就返回 503。前端会据此在启动页显示「服务维护中」而不是让玩家一直转圈。
3. **说明服务的可用时间窗口**。如果 DevBox 会自动休眠，请告诉我们休眠策略，
   前端好安排联调时间；如果能常驻，请配上自动重启。

## 二、P1 接口契约问题（前端已本地兜底，但建议后端改）

### 2.1 互动类接口幂等回放时缺 `duplicated` 字段 ⭐ 最想要的一条

对接文档 1.6 说「部分接口的响应里有 `duplicated: true`，表示这次是回放而非真实执行，
前端不要重复播放『获得奖励』动画」。

**实测：四个互动接口没有这个字段。** 同一个 `bizId` 调两次 `POST /pet/feed`：

```
第 1 次：{"pet":{...,"intimacy":2,...},"gained":{"intimacy":2,"exp":5,"coin":3},"gameCoin":3}
第 2 次：{"pet":{...,"intimacy":2,...},"gained":{"intimacy":2,"exp":5,"coin":3},"gameCoin":3}
```

两次响应**逐字节相同**。幂等本身是对的（钱没多扣、奖没多发），
但前端拿到第二次响应时没法判断这是回放，结果就是：
弱网重试成功后，玩家会看到「亲密 +2 经验 +5 金币 +3」的飘字**再飘一遍**，
余额却没变——玩家会以为掉奖励了，来提工单。

**请求**：给所有幂等写接口统一加 `duplicated: boolean`。目前缺这个字段的接口：

| 接口 | 回放时会重复播放的表现 |
| --- | --- |
| `POST /pet/feed` / `bath` / `pet` / `play` | 收益飘字、升级动画 |
| `POST /pet/offline/claim` | 离线收益结算弹窗 |
| `POST /daily/checkin` | 签到奖励动画 |
| `POST /daily/task/claim` | 任务领奖动画 |
| `POST /dex/claim` | 图鉴解锁演出 |
| `POST /ad/verify` | 广告奖励飘字 |
| `POST /boost/speedup` / `POST /stamina/recover` | 消费提示 |

（`/race/settle`、`/race/reward/double`、`BuyResult` 系列已经有了，行为正确。）

### 2.2 冷却 429 的秒数只能从中文文案里正则抠

`POST /pet/feed` 冷却中返回 `429 {"code":429,"message":"冷却中，还需 18 秒"}`。

前端目前用 `/(\d+)\s*秒/` 从 message 里抠数字来校正本地倒计时。
这个做法很脆：文案改成「请等待 18 秒后再试」前端倒计时就静默失效了，
而且失效方式是「按钮一直灰着」，很难被测出来。

**请求**：429 响应体加一个结构化字段，例如
`{"code":429,"message":"冷却中，还需 18 秒","cooldownRemainMs":18000}`。
和成功响应里的 `cooldownRemainMs` 同名同单位即可。

### 2.3 新号的 `equipped` 是空对象

`GET /wardrobe` 在新号上返回 `"equipped": {}`，但 `skin_default`（原色皮肤）和
`bg_room`（暖阳小屋背景）是 `price: 0` 且 `owned: true` 的默认物品。

直接按 `equipped` 渲染的话，新玩家进游戏会看到一只**没有皮肤、没有背景**的宠物。

前端已经加了兜底（同槽位挑最便宜的已拥有物品补上 `body` 和 `bg`），
但这属于「每个客户端各自猜一遍默认形象」，将来出 iOS/安卓/H5 多端容易不一致。

**请确认**：建号时是否应该由后端自动穿戴默认外观？
如果确定交给前端兜底也行，请回一句确认，我们把规则写进文档固化下来。

### 2.4 背景类物品的 `type` 是 `accessory`

```json
{ "key": "bg_beach", "type": "accessory", "name": "海边夕照", "slot": "bg", ... }
```

对接文档 10.1 的表格把它们归为「背景」类，但接口里 `type` 是 `accessory`，
只能靠 `slot === 'bg'` 区分。前端已按 `slot` 分组渲染。

**请确认**这是设计意图（`type` 只区分皮肤/非皮肤，槽位才是真正的分类维度），
还是 `type` 漏了 `background` 枚举值。

### 2.5 `/daily` 首日签到奖励与文档公式对不上

对接文档 7.1 写签到奖励是 `min(100, 20 + (streak - 1) * 10)`。
实测新号 `streak: 0` 时 `todayReward` 返回 **20**，按公式应为 10。

前端只展示接口返回值、不自己算，所以不影响功能。
**请确认**是文档公式写错，还是实现里 streak 的语义是「本次签到后的连签数」。

## 三、P2 前端需要、但文档里还没有的能力

### 3.1 服务端时间（对时）

前端要在两次请求之间把饱食/清洁/心情的进度条**平滑地推下去**
（对接文档 5.6 的衰减公式），这就得知道「距离 `lastSeenAt` 过了多久」。

按铁律不能信任客户端时钟——玩家把系统时间调后一天，进度条就会瞬间掉到 0。

前端目前借用 `GET /health` 返回的 `time` 字段来算时钟偏移（用 RTT/2 补偿单程延迟）。

**请确认**：`/health` 的 `time` 可以长期当作对时依据吗？
如果 `/health` 将来会被网关缓存或改造，请单独给一个 `GET /time`。

### 3.2 配置版本号

对接文档附录说：价格、奖励、冷却、赛道参数、掉率、库存等所有数值
「运营可以在后台随时调整，调整后无需重启、即时生效」。

前端会缓存商店商品、赛道列表、任务列表这类不常变的数据，否则每次开面板都要转圈。
但缓存就有一个问题：**运营改完之后，前端不知道自己缓存的是旧的。**

**请求**：提供一个配置版本标识，形式不限，任选其一即可：

- `/health` 响应里加 `configVersion: "20260826-3"`；
- 或所有响应统一带一个 `X-Config-Version` 响应头。

前端每次请求都会看一眼，版本变了就把本地配置缓存清掉重拉。
这样运营改一个价格，玩家不用重进游戏就能看到。

### 3.3 未核销的广告凭证是否退回当日额度

`POST /ad/token` 每次调用签发一枚新凭证，并且**立刻占用当日额度**（`remaining` 会减 1）。

问题在于领了凭证之后广告不一定播得成：素材加载失败、玩家中途划掉、
或者播完了但核销请求断网。这几种情况下凭证不会被核销，就这么烂掉了。

按铁律「软失败不死亡，广告失败给保底」，玩家不该因为网络差就白白少几次机会。

**请确认**：凭证过期（TTL 300 秒）未核销时，当日额度会退回吗？

- 如果**会退**：请告诉我们退回的时机，前端好决定 `remaining` 什么时候重新拉。
- 如果**不退**：建议改成「核销时才扣额度」。或者至少给一个作废接口
  `POST /ad/token/abandon { nonce }`，前端在玩家划掉广告时主动归还。

### 3.4 实时通道（WebSocket）

项目规则里写明「实时用原生 `wx.connectSocket`，不用 socket.io」，
但当前对接文档里**一个实时接口都没有**，赛跑是纯 HTTP 的单机异步玩法
（`start` 时名次就算定了，对手是影子数据）。

**请确认**：近期是否规划实时对战、实时排行榜、好友互动这类功能？

- 如果**暂时不做**：前端就不预留 WebSocket 层，回一句确认即可。
- 如果**要做**：请提供 ws 地址、鉴权方式（是否复用 JWT）、心跳间隔、
  消息编号与重连补发的约定。这部分前端要自己实现心跳和重连，需要提前对齐协议。

### 3.5 封禁态的测试账号

对接文档 1.3 说被封禁玩家「读接口仍可访问，写接口返回 403」，
前端要为此做一个专门的封禁提示弹窗（展示原因 + 客服入口），而不是静默失败。

这个分支现在**没法自测**——三个预置账号都是正常态。

**请求**：加一个 `mock:banned` 预置账号，或者提供后台切封禁态的操作方式。
最好连「带原因的封禁」也覆盖到，我们要验证 `账号已被封禁：{原因}` 的文案渲染。

### 3.6 兑换订单状态变更的通知方式

订单 `pending → shipped` 是运营在后台操作的，前端目前只能靠玩家自己进订单页
`GET /exchange/orders` 轮询才能看到发货。

**请确认**两件事：

1. 轮询频率上限是多少？前端准备在订单页每 30 秒拉一次，页面关掉就停，是否可接受？
2. 是否考虑接入微信订阅消息推送发货通知？如果要，需要后端提供下发接口，
   前端负责在下单时调 `wx.requestSubscribeMessage` 拿授权。

### 3.7 物种（species）的取值与新手选择流程 ⭐ 新增

产品已确定宠物做**猫、狗两种**。接口层有三个问题需要明确，
否则前端没法按物种去取模型和贴图。

**（1）`species` 的枚举值是什么？**

现在 `/pet/state` 返回的是 `"default"`。前端建议用 `"cat"` / `"dog"`，
请后端确认取值并固定下来——这个字符串会被前端拿去拼资源路径
（`skin_snow_cat.png` 这种），定了之后不方便改。

**（2）新玩家怎么选物种？这条是设计冲突，需要产品和后端一起定。**

对接文档 5.1 写明：`GET /pet/state` 在玩家还没有宠物时会**自动创建一只**并返回，
「前端不需要处理『无宠』分支」。这在单物种时很方便，但现在有两个物种，
如果产品要让玩家在新手引导里选猫还是狗，**自动建宠会抢先建出一只 `default`，
玩家的选择就没意义了**。

三个可选方案，请后端和产品选一个：

| 方案 | 做法 | 影响 |
| --- | --- | --- |
| A | 自动建宠保留，但允许后续改物种（新增接口或 `/pet/active` 扩展） | 前端改动小，但"改物种"这个操作在养成品类里语义奇怪 |
| B | `/pet/state` 增加一个「不自动建宠」的模式，新手流程改走 `/pet/create` | 最符合直觉，但要改接口行为 |
| C | 自动建宠时随机分配物种，玩家不能选 | 最省事，但削弱新手代入感 |

前端目前按 B 的思路预留，冷启动仍先调 `/pet/state`，
拿到 `species === 'default'` 时会当作"未选择"处理。**请确认这个假设是否成立。**

**（3）换装商店要不要按物种过滤？如果要过滤，请用「体型 ID」而不是「物种」。**

`GET /wardrobe` 现在返回一份全局列表，物品不带物种信息。

- **皮肤**：前端能自己解决——同一个 `itemKey` 按当前宠物的 `species`
  拼不同贴图路径，接口不用改。
- **配饰**：现阶段按"猫狗全通用"实现（共用骨架和挂点，一顶帽子两边都能戴），
  **现在不需要任何接口改动**。

**但如果将来要做配饰兼容性过滤，请不要用 `species` 做判据。**

参考 Neopets 换装系统（50+ 物种跑了二十年）的做法：兼容键是**体型 ID**，
不是物种也不是品种。同一形状的不同颜色共用一个体型 ID，配饰通用；
形状变了才换体型 ID。

落到接口上，将来需要的是：

- `PetStateView` 增加 `bodyId`（string 或 int）
- `WardrobeItem` 增加 `bodyIds`（该配饰适配哪些体型，空表示通用）

这样运营新增品种时，只要沿用现有体型，配饰立刻全部可用、一件都不用补配置；
只有真正改了体型的才需要额外标注。按 `species` 过滤的话，
每加一个物种都要把所有配饰重新标一遍，配置量随物种数线性增长。

**现在不用做**，只是提前对齐口径，避免将来加了 `species` 过滤再返工。

另外提一句命名：`skin_tiger`（虎纹）、`skin_calico`（三花）是猫的花色叫法，
做成狗有点违和。前端不受影响（按 key 取资源），
但如果运营觉得需要改成物种中性的名字，改配置即可，越早改成本越低。

### 3.8 静态资源地址（3D 模型与贴图）

这条**不一定是后端做**，但需要有人给一个明确的地址，所以一并列在这里。

按项目规则，主包必须 ≤ 4MB，3D 模型和场景要走 Asset Bundle 远程加载。
需要一个能配进微信 `downloadFile` 合法域名的静态资源地址（对象存储或 CDN 均可），
并支持 CORS。

美术资源前端会按 `itemKey` 命名（`skin_snow.png`、`furn_sofa.png`），
这样运营新增商品时前端只补图、不发版。

只需要针对下面这些回一句话，前端就能继续往下推：

1. 服务什么时候能恢复？根因是什么？DevBox 会自动休眠吗？
2. `/health` 能否加上 db/redis 的依赖探活？
3. 能否给所有幂等写接口统一补 `duplicated` 字段？（最影响体验的一条）
4. 429 响应能否加结构化的 `cooldownRemainMs`？
5. 新号的默认外观（皮肤/背景）由后端自动穿戴，还是前端兜底？
6. 背景物品的 `type: "accessory"` 是设计意图吗？
7. `/daily` 首日 `todayReward: 20` 是文档写错还是实现口径不同？
8. `/health` 的 `time` 能否长期作为对时依据？
9. 能否提供配置版本号，让前端知道运营改了配置？
10. 未核销的广告凭证会退回当日额度吗？
11. 近期有实时（WebSocket）需求吗？
12. 能否加一个 `mock:banned` 测试账号？
13. 订单轮询频率上限？要不要接订阅消息？
14. 静态资源（3D 模型）放哪个地址？
15. **`species` 的枚举值定成什么？**（前端建议 `cat` / `dog`，会用来拼资源路径）
16. **新玩家怎么选物种？** `/pet/state` 自动建宠会和"让玩家选猫还是狗"冲突，见 3.7（2）
17. 换装商店将来要不要按物种过滤？（现阶段前端按"配饰全通用"实现）

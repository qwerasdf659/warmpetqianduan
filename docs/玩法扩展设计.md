# 玩法扩展设计：六大玩法落地方案

> 目标：把《竞品玩法梳理》里 Neopets / Adopt Me! / 模拟人生猫狗的核心玩法，
> 全部在微信小游戏里实现。
> 前提：**自娱 / 内部演示定位**，**保留「全程不接入支付」铁律**。
> 所有经济行为走**游戏币闭环**，不碰真钱、不碰营销积分池。

---

## 零、总原则

### 0.1 铁律怎么遵守

### 0.0 经济策略：不做封顶

本项目是**自娱 / 演示定位**，没有付费、没有玩家间竞争压力。
游戏币多寡不影响体验，**玩得爽比数值平衡重要**。

因此明确不做：每日产出封顶、交易手续费、每日次数上限、通胀调控。

保留的只有**技术性约束**（防作弊校验、幂等、流水记录），
这些和经济平衡无关，是数据正确性的要求。

> 唯一需要后端配合的：现有的每日封顶（亲密 100 / 经验 200 / 币 500）
> 是**后端已实现并在生效的行为**，互动接口返回的 `capped` 字段就来自它。
> 要放开得后端改配置，前端改不了。已列入第十一节的扩展需求。

### 0.1 铁律怎么遵守

| 铁律 | 在本方案中的落地 |
| --- | --- |
| 服务端权威 | 繁殖结果、对战判定、疾病触发、交易撮合**全部后端算**，客户端只提交意图 |
| 不信任客户端时钟 | 孵化倒计时、拍卖截止、疾病进展一律用服务端时间 |
| 软失败不死亡 | 宠物永不死亡；生病只降收益，繁殖失败退还材料，对战失败不掉宠 |
| 双池隔离 | **交易、拍卖、繁殖、看病全部只用游戏币**，营销积分完全不参与 |
| 积分只向下兑权益 | 交易是「游戏币 ↔ 虚拟物品」，没有任何反向出口 |

**为什么不接支付也能做交易和稀有度**：竞品里稀缺性要靠真钱才有价值，
是因为它们的稀有物可以换钱。我们换个出口——**稀缺性的价值兑现在游戏币和图鉴上**：
稀有宠物能卖高价游戏币，游戏币能买家具皮肤、能繁殖、能看病。
闭环内部自洽，不需要外部货币。

### 0.2 前端先行的工作方式

后端目前 13 个 Controller 全是 HTTP，这六项玩法**一个接口都没有**。

推进方式不是干等：

```
前端在假后端（_research/mock-server.mjs）里定义接口
        ↓
前端照着实现，本地跑通、能玩
        ↓
把「带真实请求/响应样例的接口契约」交给后端
        ↓
后端实现 → 前端切回真实地址（改 DEV_BASE_URL 一处）
```

**用可运行的实现去定义需求，比写纸面需求准确得多。**
本文档每一节的「接口契约」就是给后端的交付物。

### 0.3 实施顺序

按「性价比 × 依赖关系」排：

| 阶段 | 内容 | 依赖 | 后端工作量 |
| --- | --- | --- | --- |
| **P0** | 成长阶段 stage | 无，数据已有 | **零** |
| **P1** | 疾病与治疗 | 无 | 小 |
| **P2** | Petpet 套娃 | 复用换装槽位 | 小 |
| **P3** | 繁殖遗传 | 需 stage | 中 |
| **P4** | 异步 PvP | 复用赛跑 | 中 |
| **P5** | 交易 + 拍卖行 | 需繁殖产出稀有度 | 大 |
| **P6** | 实时 PvP（WebSocket） | 需 P4 | **最大** |
| **P7** | 兽医经营 | 需 P1 | 大 |
| **P8** | 稀有度分级 + 融合形态 | 需 P3 繁殖 | 中 |
| **P9** | 社交展示（好友榜 / 家园访问） | 需 P8 | 中 |
| **P10** | 性格特质 + 沉浸模式 | 无 | **小**（仅扩字段） |
| **P11** | 小游戏赚币 | 无 | 中 |
| **P12** | 限时活动 | 需 P8 稀有度 | 小 |
| **P13** | 训练技巧 | 无 | 中 |

**推荐执行顺序不等于编号顺序。** 按「性价比 × 后端依赖」重排：

```
P0  成长阶段      零后端，先做
P10 性格特质      仅扩字段，和 P0 一起做性价比最高
P1  疾病治疗      后端小改
P13 训练技巧      深化现有陪玩
P2  Petpet        复用换装
P11 小游戏        独立模块，不阻塞别的
P3  繁殖遗传      开始变重
P8  稀有度+融合   依赖 P3
P12 限时活动      依赖 P8
P9  社交展示      依赖 P8，让稀缺被看见
P4  异步 PvP
P5  交易+拍卖行
P7  兽医经营
P6  实时 PvP      最后，需要和后端定协议
```

> **P8 和 P9 是一对，不能只做一个。** 稀有度和融合是"造稀缺"，
> 社交展示是"让稀缺被看见"。只做前者，玩家攒了一堆传说宠物没人知道，
> 攀比动机不成立——这正是 Adopt Me 那套在无交易环境下容易变空壳的原因。
> 我们用**展示**替代它的**交易**来兑现稀缺价值。

**P0 现在就能做，不需要后端动任何东西。**

## 一、P0 · 成长阶段（stage）

### 玩法

对标 Adopt Me 的「新生 → 幼年 → 成年」。宠物随等级成长，外形跟着变。

**接口里已经有 `stage` 字段，前端完全没用**——这是全部六项里唯一
「数据现成、只差表现」的一项，性价比最高。

| stage | 等级 | 表现 |
| --- | --- | --- |
| `baby` | 1–5 | 缩放 0.72，头身比更大，动作幅度小、频率快 |
| `teen` | 6–15 | 缩放 0.86 |
| `adult` | 16–100 | 缩放 1.0 |

### 实现要点

- 缩放走宠物根节点，**配饰会自动跟着缩放**（挂点传递完整世界矩阵，见 UI 规范 5.3）。
- 阶段切换时播一次放大回弹 + 粒子，配合升级动画。
- 幼年期把 `idle` 动画播放速度调到 1.15 倍——**幼崽动作更碎更快**，
  不用额外做动画就能表达年龄差。

### 接口

**无需新增。** `PetStateView.stage` 已存在。

## 二、P1 · 疾病与治疗

### 玩法

对标模拟人生的兽医系统 + Neopets 的「不会死但会限制玩法」。

长期疏于照顾 → 宠物生病 → 收益下降 → 需要治疗。

**严格遵守「软失败不死亡」**：生病**只降低收益、不影响任何已有资产**，
不会丢宠物、不会掉等级、不会扣已获得的币。

### 触发与效果

| 病症 | 触发条件（服务端判定） | 效果 |
| --- | --- | --- |
| `hungry_weak` 营养不良 | 饱食 = 0 持续 12 小时 | 离线时薪 −30% |
| `dirty_flea` 跳蚤 | 清洁 = 0 持续 12 小时 | 互动亲密收益 −50% |
| `low_mood` 抑郁 | 心情 = 0 持续 24 小时 | 赛跑成绩 −10% |

三种病可以叠加，但**不会导致任何不可逆损失**。

### 治疗

| 方式 | 消耗 | 效果 |
| --- | --- | --- |
| 用药（消耗品） | `cons_medicine` ×1 | 立即治愈一种 |
| 看诊（花币） | 200 游戏币 | 治愈全部 |
| 自愈 | 对应属性回到 60 以上并维持 6 小时 | 免费但慢 |

自愈这条很重要——**玩家没币也一定有出路**，符合软失败原则。

### 接口契约（给后端）

```
GET /pet/health
→ { "conditions": [
      { "key": "dirty_flea", "name": "跳蚤",
        "desc": "清洁长期为 0 导致，亲密收益减半",
        "since": "2026-08-26T12:00:00.000Z",
        "effect": { "intimacyRate": -0.5 },
        "curedBy": ["cons_medicine", "clinic"] }
    ] }

POST /pet/cure   { bizId, petId?, method: "item" | "clinic" }
→ { "pet": PetStateView, "cured": ["dirty_flea"], "gameCoin": 1180 }
```

- `POST /pet/cure` **必须幂等**（涉及扣币/扣道具）。
- 错误：400 `该宠物没有需要治疗的病症` / `余额不足` / `该消耗品数量不足`。
- 新增消耗品 `cons_medicine`（价格 150，走现有 `/items/consumables`，仅需加配置）。

### 前端

主界面宠物头顶挂病症图标，点开看详情和治疗入口。
属性条下方加一行病症提示（`danger` 色）。

## 三、P2 · Petpet 套娃

### 玩法

对标 Neopets 的 Petpet——**你的宠物也能养一只小宠物**。

这是个「低成本高感知」的设计：一只小挂件跟在宠物身边，
提供被动加成，且是收集品。

### 设计

- Petpet 是一个**新的换装槽位** `pet`（复用整套换装机制，后端改动最小）。
- 每只宠物同时只能带 1 只 Petpet。
- 提供**被动加成**，这是它区别于纯装饰配饰的地方：

| itemKey | 名称 | 获取 | 加成 |
| --- | --- | --- | --- |
| `pp_bird` | 小鸟 | 商店 800 币 | 离线时薪 +5% |
| `pp_fish` | 小鱼 | 商店 1200 币 | 互动经验 +10% |
| `pp_bug` | 瓢虫 | 扭蛋稀有档 | 赛跑成绩 +3% |
| `pp_ghost` | 小幽灵 | 图鉴奖励 | 心情衰减 −10% |

> ⚠️ **注意这违反了现有的「换装纯外观」约定。**
> 现在的规则是「换装只影响外观，速度耐力只由等级决定」。
> Petpet 带数值加成就打破了这条。
> **建议：加成只作用于「收益类」数值（时薪、经验、心情衰减），
> 不碰速度和耐力**，这样赛跑的公平性不受影响，也不会让换装变成数值付费点。

### 接口契约

复用现有换装接口，只需后端：
1. `Slot` 枚举增加 `"pet"`
2. `WardrobeItem` 增加 `bonus` 字段：`{ "offlineRate": 0.05 }`
3. 离线收益、互动收益、赛跑结算时把加成算进去（**服务端算，前端只展示**）

```
GET /wardrobe → items 里新增 slot="pet" 的条目，带 bonus
POST /wardrobe/equip { itemKey: "pp_bird" }   // 无需改动
```

### 前端

Petpet 作为独立小模型挂在宠物脚边（不用挂点，直接放在宠物根节点下偏移位置），
带自己的待机浮动动画。美术需求：4 个 Petpet 模型，各 ≤ 300 三角面。

## 四、P3 · 繁殖遗传

### 玩法

对标模拟人生的配种遗传 + Adopt Me 的孵蛋。

两只成年宠物配对 → 产蛋 → 孵化 → 得到一只新宠物，外观特征来自父母。

### 规则设计

| 项 | 规则 |
| --- | --- |
| 前提 | 双方都是 `adult`（≥16 级），且都不在冷却中 |
| 消耗 | 500 游戏币 + 双方各扣 30 体力 |
| 冷却 | 每只宠物繁殖后冷却 24 小时 |
| 孵化 | 服务端时间 4 小时，可看广告或花币加速 |
| 上限 | 受现有「最多 6 只宠物」限制，满了不能孵 |

### 遗传规则（服务端计算）

**物种**：50% 随父，50% 随母。异种配对（猫×狗）产出随机一方。

**毛色（皮肤）**：借鉴显隐性基因模型——每只宠物携带**两个皮肤基因**，
显示的是显性的那个：

```
显性顺序：skin_default > skin_snow > skin_tiger > skin_calico > skin_shadow
（越稀有越隐性，所以稀有花色需要几代培育才能显现）
```

子代从父母各随机继承一个基因。**两只普通外观的宠物可能携带同一个隐性稀有基因，
配出一只稀有花色**——这正是遗传玩法的乐趣所在，也天然制造了稀缺性。

**初始属性**：等级 1，但 `staminaMax` 继承父母均值的 10% 加成（上限 +20%）。

### 接口契约

```
POST /breed/start   { bizId, petAId, petBId }
→ { "eggId": "12", "hatchAt": "2026-08-27T04:00:00.000Z",
    "gameCoin": 4500, "cooldownUntil": {...} }

GET /breed/eggs
→ { "eggs": [ { "id": "12", "hatchAt": "...", "remainSec": 12800,
                "parentA": "3", "parentB": "7" } ] }

POST /breed/speedup { bizId, eggId, method: "ad" | "coin", adToken? }
→ { "egg": {...}, "gameCoin": 4300 }

POST /breed/hatch   { bizId, eggId }
→ { "pet": PetStateView, "inherited": { "species": "cat",
      "genes": ["skin_snow", "skin_shadow"], "visible": "skin_snow" },
    "duplicated": false }
```

- 全部写接口**必须幂等**。
- `hatchAt` 是服务端时间，前端只做倒计时展示，到点后调 `hatch` 由服务端裁决。
- 错误：400 `宠物未成年` / `宠物繁殖冷却中` / `体力不足` / `余额不足` /
  `最多只能养 6 只宠物` / `尚未到孵化时间`。

### 前端

新增繁殖页：选两只宠物 → 显示消耗和冷却 → 确认 → 蛋列表带倒计时 → 孵化开蛋动画。
基因不可见（只展示显性花色），**否则遗传玩法的悬念就没了**。

## 五、P4 · 异步 PvP（先做这个）

### 为什么先做异步

真实时对战要 WebSocket，是六项里工作量最大的。
但**赛跑玩法本身已经是异步对战了**——现有 `/race/start` 的对手是影子数据，
`ghostSource` 字段已经支持 `player`（真实玩家数据）。

所以异步 PvP 几乎是**在现有赛跑上加一层匹配和排行**，不需要 WebSocket，
就能拿到 80% 的对战体验。**先上这个，再考虑实时。**

### 玩法

| 模式 | 说明 |
| --- | --- |
| 好友挑战 | 用好友的宠物数据当对手跑一场，结果双方都能看到 |
| 天梯 | 按战力匹配对手影子，胜负计积分，周结算发奖 |
| 复仇 | 被挑战失败后可发起复仇战 |

**对手是"影子"而不是真人在线**——用对方宠物的属性快照生成成绩，
这跟现有赛跑的机制完全一致，服务端权威也天然满足。

### 接口契约

```
GET  /pvp/opponents           // 按战力匹配 3 个候选对手
→ { "opponents": [ { "userId": "88", "nickname": "小黑",
                     "petSnapshot": { "level": 9, "power": 52, "skin": "skin_snow" },
                     "rankPoint": 1240 } ] }

POST /pvp/challenge  { bizId, opponentUserId, trackKey }
→ { "matchId": "9", "myFinishTime": 23.1, "oppFinishTime": 24.6,
    "win": true, "rankPointDelta": +18, "rewardCoin": 60,
    "gameCoin": 4560, "duplicated": false }

GET  /pvp/rank?page=1&pageSize=20
→ { "list": [...], "total": 200, "myRank": 37, "myRankPoint": 1240 }

GET  /pvp/history?page=1       // 含被别人挑战的记录，用于"复仇"
```

- 挑战**必须幂等**（发奖）。
- **战报由服务端生成**，前端只负责用 `finishTime` 播动画。
- 排行榜按周结算，服务端定时发奖。

### 前端

赛跑页加「挑战」Tab，复用现有赛跑动画（两条跑道而不是四条）。
排行榜列表 + 我的排名。

## 六、P5 · 交易 + 拍卖行

### 玩法

对标 Adopt Me 的交易经济，但**全程游戏币计价，不碰真钱**。

### 两种形态

**一、直接交易**：双方各自摆出物品 + 游戏币，双方确认后成交。

**二、拍卖行**：挂单出售，其他玩家出价竞拍，到期价高者得。

### 可交易范围

| 可交易 | 不可交易 | 原因 |
| --- | --- | --- |
| 配饰、皮肤、家具、消耗品 | **营销积分** | 铁律：双池隔离 |
| Petpet | **兑换订单/实物** | 已核销的权益不可回流 |
| 繁殖产出的宠物 | **出战宠** | 避免误操作 |

### 不设手续费与交易次数限制

**不做经济调控。** 自娱定位，游戏币多寡不影响体验，
手续费和次数上限只会让玩家嫌麻烦。

只保留两条**技术性**约束，和经济无关：

| 措施 | 目的 |
| --- | --- |
| 交易全程记流水（`reason: "trade"`） | 可追溯，出问题能查 |
| 出价时冻结游戏币，被超越自动解冻 | 防止余额不足时成交失败 |

### 接口契约

```
POST /trade/offer   { bizId, targetUserId, giveItems[], giveCoin, wantItems[], wantCoin }
→ { "tradeId": "5", "status": "pending" }

POST /trade/respond { bizId, tradeId, accept: true }
→ { "trade": {...}, "wallet": WalletView, "duplicated": false }

GET  /auction?page=1&sort=endingSoon|priceAsc
→ { "list": [ { "id": "31", "itemKey": "skin_shadow", "seller": "88",
                "currentBid": 2400, "bidCount": 3,
                "endAt": "2026-08-27T10:00:00.000Z" } ], "total": 57 }

POST /auction/list   { bizId, itemKey, qty, startPrice, durationHours }
POST /auction/bid    { bizId, auctionId, price }
POST /auction/claim  { bizId, auctionId }        // 领取拍得物品或流拍退回
```

- 出价**必须服务端加锁**（并发竞价），复用现有玩家级锁机制。
- 出价立即冻结游戏币，被超越后自动解冻——**冻结/解冻都要走流水**。
- `endAt` 用服务端时间，前端倒计时仅供展示，结算以服务端为准。

### 前端

拍卖行列表（按结束时间/价格排序）+ 我的挂单 + 我的出价 + 交易请求收件箱。
这是六项里前端界面最重的一块。

## 七、P6 · 实时 PvP（WebSocket）

### 为什么放最后

这是唯一需要引入**全新通讯层**的玩法。项目规则要求实时用原生
`wx.connectSocket`（禁止 socket.io），心跳、重连、消息编号全要自己实现。

**建议先上 P4 异步 PvP 验证玩法，确认玩家真的要实时再做。**

### 需要和后端对齐的协议

这部分**必须双方一起定**，不能单方面出方案：

| 项 | 需要明确 |
| --- | --- |
| 连接地址 | `wss://` 域名，需配进微信 socket 合法域名 |
| 鉴权 | 复用 JWT？连接时带 token 还是首帧发送？ |
| 心跳 | 间隔、超时判定、服务端是否回 pong |
| 重连 | 断线后能否恢复对局？恢复窗口多久？ |
| 消息编号 | 单调递增序号 + 补发机制，防丢包乱序 |
| 消息格式 | JSON 还是二进制？字段命名规范？ |
| 帧同步 or 状态同步 | 赛跑这类短对局建议**状态同步**，实现简单、抗延迟 |

### 前端要做的

`assets/scripts/net/socket.ts`：连接管理、心跳、指数退避重连、消息队列、
序号校验、断线期间的操作缓存。这一层要独立于业务，
和现有 `request.ts` 平级。

## 八、P7 · 兽医经营

### 玩法

对标模拟人生的兽医诊所——**玩家自己开诊所，给别的玩家的宠物看病赚币**。

这是六项里唯一的「经营」玩法，也是很好的游戏币产出口。

### 设计

| 项 | 规则 |
| --- | --- |
| 开诊所 | 消耗 5000 游戏币解锁 |
| 接诊 | 系统按 P1 的病症生成病例（可掺入真实玩家宠物的快照） |
| 诊断 | 观察症状 → 选择正确治疗方案（小玩法） |
| 收益 | 诊断正确得币，错误只得一半 |
| 评分 | 累计正确率影响诊所星级，星级决定单次收益 |
| 上限 | 不限次数，想接多少接多少 |

诊断小玩法本身是**纯客户端表现**，但**正确答案和发币必须服务端判定**——
否则客户端一改就无限刷币。做法：服务端下发病例和候选方案，
前端提交选择，服务端裁决并发币。

### 接口契约

```
POST /clinic/unlock  { bizId }
→ { "unlocked": true, "gameCoin": 0 }

GET  /clinic/case                 // 领一个病例，服务端不下发答案
→ { "caseId": "77", "symptoms": ["抓挠", "毛发脱落"],
    "options": [ { "key": "flea_med", "name": "驱虫药" },
                 { "key": "vitamin", "name": "维生素" } ] }

POST /clinic/diagnose { bizId, caseId, optionKey }
→ { "correct": true, "rewardCoin": 120, "gameCoin": 4680,
    "clinicStar": 3, "duplicated": false }
```

- 不限每日接诊次数。
- 错误：400 `诊所未解锁` / `病例已过期`。

## 九、P8 · 稀有度分级与融合形态

### 9.1 稀有度分级

前面几节零散提到"稀有花色"，但没有成体系。这里统一定义。

**五档分级**，对标 Adopt Me，适用于宠物、Petpet、配饰、皮肤：

| 稀有度 | key | 边框色 | 来源 |
| --- | --- | --- | --- |
| 普通 | `common` | `#7D7791` | 商店、初始 |
| 优秀 | `uncommon` | `#6DDF9C` | 商店高价、任务 |
| 稀有 | `rare` | `#7AC8FF` | 扭蛋、繁殖隐性基因 |
| 史诗 | `epic` | `#C89BFF` | 扭蛋保底、融合一级 |
| 传说 | `legendary` | `#FFD166` | 融合二级、限时活动 |

**统一表现规范**：物品卡片用稀有度色描边 + 背景微渐变，
传说档加持续粒子。**颜色不能是唯一区分手段**（色盲玩家），
边框粗细也要跟着分档：普通 2px、稀有 3px、传说 4px + 角标。

### 9.2 融合形态

对标 Adopt Me 的霓虹（Neon）与超级霓虹（Mega Neon），
这是它「16 只换 1 只」的深度来源。

**但我们有个硬约束：后端限制最多养 6 只宠物。**

4 只换 1 只需要同时持有 4 只同花色成年宠物，占掉 6 个位置里的 4 个，勉强可行；
16 只换 1 只**完全不可能**。所以要么改数值，要么改上限。

**方案 A（推荐）：降低融合门槛，不改后端上限**

| 融合 | 材料 | 产出 | 稀有度 |
| --- | --- | --- | --- |
| 一级「辉光」 | 3 只同花色成年宠物 | 1 只辉光形态 | `epic` |
| 二级「虹彩」 | 3 只辉光形态 | 1 只虹彩形态 | `legendary` |

3 只一组，占位可控。二级需要累计培育 9 只，是长线目标但不至于卡死。

**方案 B：后端把「6 只上限」拆成「出战位 + 仓库」**

```
出战位 6 个（现有逻辑不变）
仓库    30 个（只存放，不参与衰减结算，不产出离线收益）
```

这样才能支撑 4→1→4→1 的原版比例，也顺带解决交易和繁殖的存放问题。
**这是接口变更，需要后端确认**（见第十节）。

> 建议先按方案 A 做，验证融合玩法有没有人玩，再决定要不要投入做仓库。

**融合形态的表现**（美术需求）：

| 形态 | 表现 |
| --- | --- |
| 辉光 | 自发光材质（emissive）+ 缓慢呼吸光效 |
| 虹彩 | 自发光 + 色相循环动画 + 常驻粒子 |

**这两个形态不需要新模型**——沿用现有网格，只换材质和加粒子，
成本极低但视觉冲击强。这正是 Adopt Me 的做法。

### 9.3 接口契约

```
POST /fusion/preview  { petIds: ["3","7","9"] }
→ { "ok": true, "resultForm": "glow", "resultRarity": "epic",
    "consumes": ["3","7","9"], "warning": "材料宠物将被消耗且不可恢复" }

POST /fusion/execute  { bizId, petIds: ["3","7","9"] }
→ { "pet": PetStateView, "form": "glow", "rarity": "epic",
    "duplicated": false }
```

- `preview` 必须存在——**融合会永久消耗宠物，是全游戏唯一不可逆的操作**，
  必须让玩家先看清后果再确认。前端要弹二次确认。
- `execute` 必须幂等。
- `PetStateView` 需增加 `form`（`normal` / `glow` / `rainbow`）和 `rarity` 字段。
- 错误：400 `材料宠物花色不一致` / `材料宠物未成年` / `材料宠物数量不足` /
  `出战宠不能作为材料`。

> ⚠️ **和「软失败不死亡」铁律的关系**：融合会消耗宠物，看似冲突。
> 区别在于——这是**玩家主动发起、有明确预览和二次确认的等价交换**，
> 不是"疏于照顾导致失去"。铁律禁止的是后者。
> 但仍建议：出战宠禁止作为材料，避免误操作。

## 十、P9 · 社交展示（攀比出口）

### 10.1 为什么必须有

稀有度和融合做完，如果没人看得见，攀比就不成立——
**Adopt Me 的暗影龙值钱，是因为别人能看见你牵着它。**

这是前面所有稀有度设计能否生效的前提，不是可选项。

### 10.2 三个出口

**一、好友榜（走开放数据域，不经过自有后端）**

项目规则明确：好友关系链和好友榜走**微信开放数据域 + 托管 KV**，
不经过自有后端。所以这块**不需要后端接口**，但需要：

- 建 `openDataContext` 子域工程
- 主域通过 `wx.getOpenDataContext().postMessage()` 把要展示的数据推过去
- 子域用 `wx.getFriendCloudStorage()` 拉好友数据并自行绘制
- 上报用 `wx.setUserCloudStorage()`

上报字段建议：最高稀有度、宠物数量、图鉴完成度、PvP 积分。

> 开放数据域是独立渲染环境，**不能访问主域的任何变量**，
> UI 要在子域里单独实现一遍。这是微信平台的限制，绕不过去。

**二、家园访问**

去别人家看他的宠物和家具布置——这是养成品类最自然的炫耀场。

```
GET /home/visit?userId=88
→ { "nickname": "小黑", "comfort": 78,
    "grid": {...}, "placed": [...],
    "pet": { "nickname": "煤球", "level": 22, "form": "glow",
             "rarity": "epic", "appearance": { "body": "skin_shadow", ... } } }

POST /home/like  { bizId, userId }     // 点赞，每人每天一次
→ { "likes": 43, "gained": 10 }         // 被访问者获得游戏币
```

点赞给被访问者发币——**让"被参观"这件事有收益**，玩家才有动力布置家园。

**三、图鉴展示墙**

复用现有 `/dex`。新增"收藏"维度：拥有过的皮肤、Petpet、融合形态都进图鉴，
完成度可以在好友榜上比。

### 10.3 前端

- 好友榜：开放数据域子域工程（独立的一套渲染代码）
- 家园访问：复用家园界面，只读模式 + 点赞按钮
- 图鉴墙：复用现有图鉴页，加收藏分类

## 十二、P10 · 性格特质

### 玩法

对标模拟人生的特质系统。**这是全部玩法里性价比最高的一项**——
几乎不增加美术和后端成本，但直接解决"每只宠物都一样"的问题。

### 设计

建号或孵化时随机分配 **1–2 个特质**，终身不变（这是"这只宠物的性格"）。

| 特质 | 表现差异 | 数值影响 |
| --- | --- | --- |
| `lively` 活泼 | 待机幅度大、频率高；气泡话多 | 陪玩收益 +10% |
| `timid` 胆小 | 待机动作小、偶尔缩一下 | 抚摸收益 +10% |
| `greedy` 贪吃 | 看到食物图标会凑过去 | 喂食收益 +10%，饱食衰减 +20% |
| `aloof` 高冷 | 待机常背对镜头 | 亲密涨得慢，但心情衰减 −20% |
| `clean` 爱干净 | 频繁舔毛动作 | 清洁衰减 −30% |
| `sleepy` 嗜睡 | 待机常趴着 | 体力恢复 +20% |

**数值影响只碰收益和衰减，绝不碰速度和耐力**——赛跑公平性不能被性格影响，
否则就变成"抽到好性格才能赢"的数值抽卡。

**有得有失是关键**：贪吃加喂食收益但饿得快，高冷减心情衰减但亲密慢。
全是纯增益的话，玩家会为了刷特质反复删号重建。

### 遗传

繁殖时子代特质来源：60% 从父母的特质池里随机继承一个，40% 全新随机。
这让繁殖多一层收集目标——**培育出想要的性格组合**。

### 接口

**无需新增接口**，只需扩展字段：

```
PetStateView 增加：
  "traits": [
    { "key": "greedy", "name": "贪吃",
      "desc": "喂食收益 +10%，但饿得也快",
      "effects": { "feedGain": 0.1, "hungerDecay": 0.2 } }
  ]
```

- 特质效果**必须服务端结算**（互动收益、衰减速率都在服务端算），
  前端只负责展示 `desc` 和挑选对应的待机动画。
- `POST /pet/create` 可选传 `traits`（仅测试用，生产环境服务端随机）。

### 前端

- 宠物名字下方显示特质标签
- 待机动画按特质选不同的一套（复用同一批动画，改播放参数即可）
- 气泡文案按特质分组，`describeMood()` 增加特质维度

## 十三、P11 · 小游戏赚币

### 玩法

对标 Neopets 的小游戏经济——**它的核心产币口**。
我们目前产币只有互动、赛跑、广告、签到、离线，来源单一。

### 三个小游戏（都复用现有 3D 场景和宠物模型）

| 小游戏 | 玩法 | 时长 |
| --- | --- | --- |
| `catch` 接飞盘 | 左右移动宠物接住落下的飞盘 | 60 秒 |
| `memory` 记忆翻牌 | 翻开配对的宠物卡片 | 不限，步数计分 |
| `rhythm` 节奏喂食 | 按节奏点击投喂 | 45 秒 |

### 防作弊（这是这个玩法的技术核心）

分数换币，**客户端提交的分数一律不可信**。三层防护：

1. **服务端下发种子**：开始时服务端返回 `seed`，前端用它生成道具序列，
   保证同一局的内容是服务端可复现的。
2. **提交操作序列而非分数**：前端提交的是玩家的操作时间戳序列，
   服务端用同一个 `seed` 回放，自己算出分数。
3. **单局收益上限**：不是为了控通胀，是为了防止校验万一被绕过时损失无界。
   每日次数不限。

> 第 2 层是关键。只做第 3 层的话，玩家每局都能拿满上限；
> 加上回放校验，作弊成本就远高于收益了。

### 产出策略

**不做经济封顶。** 本项目是自娱 / 演示定位，没有付费、没有玩家间竞争压力，
币多币少不影响体验，玩得爽比数值平衡重要。

小游戏产出独立计算，不并入互动的每日封顶。

> 现有的每日封顶（亲密 100 / 经验 200 / 币 500）是**后端已实现的行为**，
> 互动接口的 `capped` 字段就来自它。要放开需要后端改配置，见第十一节末尾。

### 接口契约

```
GET  /minigame/list
→ { "games": [ { "key": "catch", "name": "接飞盘", "maxRewardCoin": 80 } ] }

POST /minigame/start   { bizId, gameKey }
→ { "sessionId": "51", "seed": "a3f9c2...", "expiresInSec": 300 }

POST /minigame/settle  { bizId, sessionId, actions: [ { t: 1230, x: 0.4 } ] }
→ { "score": 620, "rewardCoin": 64, "gameCoin": 4820, "duplicated": false }
```

- `settle` 必须幂等。
- 不限每日次数，不并入每日封顶。
- 错误：400 `对局已过期` / `操作序列校验失败`。

## 十四、P12 · 限时活动

### 玩法

对标 Adopt Me 的限时活动宠物——**制造稀缺和回流的主要手段**。
暗影龙值钱就是因为它停产了。

### 设计

活动是**纯配置驱动**的，运营在后台配好就能上线，不发版：

| 活动类型 | 内容 |
| --- | --- |
| 限定奖池 | 扭蛋池临时加入限定形象，活动结束即下架 |
| 限定商店 | 限时上架特殊皮肤/配饰/Petpet |
| 活动任务 | 限时任务链，完成得限定奖励 |
| 登录回馈 | 活动期间每日登录额外奖励 |

**限定物品必须真的下架**，否则稀缺性不成立。这点要和运营讲清楚：
返场会稀释老玩家的收藏价值，要慎重。

### 接口契约

```
GET  /event/current
→ { "events": [
      { "key": "2026spring", "name": "春日限定",
        "type": "gacha_pool",
        "startAt": "...", "endAt": "...", "remainSec": 172800,
        "banner": "event_2026spring",
        "items": [ { "itemKey": "skin_sakura", "rarity": "legendary" } ] } ] }

GET  /event/progress?eventKey=2026spring
→ { "tasks": [...], "claimed": [...] }

POST /event/claim  { bizId, eventKey, rewardKey }
→ { "gained": {...}, "wallet": WalletView, "duplicated": false }
```

- `remainSec` 由服务端算，**前端不能用本地时间判断活动是否结束**。
- 活动结束后 `claim` 返回 400 `活动已结束`——已获得的物品保留，未领的作废。

### 前端

主界面加活动入口（有活动时才显示 + 红点），活动页按 `type` 渲染不同布局。
倒计时用服务端 `remainSec` 起本地计时，每次进页面重新对齐。

## 十五、P13 · 训练技巧

### 玩法

对标模拟人生的训练系统。**不是新系统，是现有「陪玩」的深化**。

现在陪玩只是加心情、扣体力。加上训练后，陪玩变成有目标的长期投入。

### 设计

| 技巧 | 解锁条件 | 学习消耗 |
| --- | --- | --- |
| `sit` 坐下 | Lv1 | 陪玩 5 次 |
| `shake` 握手 | Lv5 | 陪玩 10 次 |
| `roll` 打滚 | Lv10 | 陪玩 15 次 |
| `jump` 跳圈 | Lv20 | 陪玩 25 次 |
| `dance` 跳舞 | Lv30 | 陪玩 40 次 |

- 每个技巧有**熟练度 0–100**，靠反复练习提升。
- 学会后可在主界面**表演**：播放对应动画 + 获得亲密和游戏币。
- 熟练度越高，表演收益越高、动作越流畅（动画播放速度和幅度）。
- 技巧数量计入图鉴，是收集目标之一。

**和赛跑的关系**：`jump` 跳圈熟练度满后，赛跑成绩 +2%。
这是唯一影响赛跑的技巧，且需要长期投入才能拿到——**是努力的回报，不是抽卡的运气**。

### 接口契约

```
GET  /training/tricks
→ { "tricks": [ { "key": "sit", "name": "坐下", "unlocked": true,
                  "learned": true, "proficiency": 62,
                  "requireLevel": 1, "requirePlayCount": 5,
                  "playCount": 12 } ] }

POST /training/practice { bizId, trickKey, petId? }
→ { "trick": {...}, "proficiencyGain": 8, "pet": PetStateView,
    "cooldownRemainMs": 60000, "duplicated": false }

POST /training/perform  { bizId, trickKey, petId? }
→ { "gained": { "intimacy": 3, "coin": 8 }, "gameCoin": 4830, "duplicated": false }
```

- 练习消耗体力（与陪玩同一套体力池），有冷却。
- 表演收益不并入每日封顶。冷却和体力已经是天然的节流手段。
- 错误：400 `等级不足` / `陪玩次数不足，无法学习` / `尚未学会该技巧` / `体力不足`。

### 前端

宠物页加"技巧"Tab：技巧列表 + 熟练度进度条 + 练习/表演按钮。
表演时播对应动画，是展示给好友看的内容之一（关联 P9 社交展示）。

### 12.4 以其他形式已满足 / 由决策排除

早前这四项被笼统归为「主动不抄」，分类不准确。实际情况是：

| 机制 | 出处 | 真实状态 |
| --- | --- | --- |
| **宠物不可操控** | 模拟人生 | **已满足**。我们本来就没有"操控宠物"的机制——玩家点的是喂食/洗澡按钮，宠物自己反应，和模拟人生是同一个模型 |
| **每天限交三次成绩** | Neopets | **已实现**。现有每日产出上限（亲密 100 / 经验 200 / 币 500）是同一目的的更好形式：不限制次数，只限制收益，玩家想玩多久玩多久 |
| **不显示需求条** | 模拟人生 | **做成可选开关**，见下方「沉浸模式」 |
| **付费货币** | Neopets / Adopt Me | **由项目决策排除**。铁律「全程不接入支付」已确认保留 |

#### 沉浸模式（可选开关）

模拟人生刻意不显示需求条，逼玩家观察行为去揣摩——**这确实带来更强的真实感**，
只是不适合当默认值（碎片化场景下会劝退新手）。

做成设置项就两全了：

| 模式 | 表现 |
| --- | --- |
| 标准（默认） | 四条属性条 + 数值，一目了然 |
| 沉浸 | 隐藏属性条与数值，只靠宠物的**行为、气泡、待机动画**暗示状态 |

沉浸模式**纯前端**，不需要任何后端改动——数据照常拉，只是不渲染。
配合 P10 性格特质的差异化待机动画，观察线索会更丰富。

> 这一项成本极低（隐藏几个节点 + 一个设置开关），
> 但对深度玩家是很讨喜的选项。建议和 P10 一起做。

## 十三、风险与取舍

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| ~~经济通胀~~ | **已决定不管**。自娱定位，无付费无竞争，币多不影响体验 | 不做封顶、不收手续费、不限次数 |
| **换装不再纯外观** | Petpet 带数值加成，打破现有约定 | 加成只作用于收益类，不碰速度耐力 |
| **包体** | 新增 Petpet 模型、蛋、诊所场景、拍卖行 UI | 全部走远程分包；当前主包 2.09MB，余量充足 |
| **WebSocket 是硬骨头** | 协议要和后端从零对齐 | 先做 P4 异步验证玩法，实时放最后 |
| **前端界面量激增** | 拍卖行、交易、繁殖、诊所都是重界面 | 先复用 widgets 工具层；等美术到位再统一美化 |

### 一句实话

这六项做完，工作量大致相当于**把现有游戏再做一遍**。
后端有 20 个新接口要写，前端有 6 个新模块。

**建议严格按 P0 → P7 推进，每完成一阶段就跑通、能玩。**
不要六个并行——那样任何一项卡住都会拖住全部，
而且经济系统需要一项一项接进来观察平衡。

**P0 成长阶段今天就能做，不需要后端配合。**

# 06 · UI 设计规范

> 面向：前端开发 + 美术
> 现状：项目里没有任何美术资源，界面全部由代码绘制。这份规范先把设计变量定下来，
> 美术进场后按同一套 token 出图，前端换资源不用改布局。
> 代码实现在 `assets/scripts/ui/widgets.ts`，改这份文档就要同步改那里。

---

## 一、设计基调

宠物养成，偏静、暖、轻松。参照移动端 3D 休闲养成的通行做法：

- **3D 内容占主视觉**，UI 退居边缘（顶部信息条 + 底部操作区），中间大片留给宠物。
- **深底 + 暖色主色**。深底让 3D 模型的高光和轮廓跳出来，浅底会把模型压平。
- **圆角、无硬边框**。所有容器和按钮走大圆角，不用 1px 描边。
- **UI 半透**，让底下的 3D 场景透出来一点，避免界面像贴上去的一块板子。

## 二、设计 token

### 2.1 画布

| 项 | 值 | 说明 |
| --- | --- | --- |
| 设计分辨率 | 720 × 1280 | 竖屏 |
| 适配 | `fitWidth`，宽度锁 720 | **可视高度随机型宽高比变化**，纵向不能写死偏移 |
| 顶部安全区 | 胶囊按钮 bottom + 8 | 必须避让，见 `widgets.topInset()` |
| 底部安全区 | 48 | 避开全面屏手势条 |
| 页面左右边距 | 32 | |

> 纵向布局一律「顶部自上而下、底部自下而上、中间吃剩余空间」。
> 编辑器预览窗口很矮时可视高度可能只有六百多，写死偏移会直接撞在一起。

### 2.2 颜色

**奶茶米色系**，2026-08-27 定稿（概念图见 `assets/style-ui-latte.png`）。

这是**浅底**方案：底色暖米白，文字深棕。

| --- | --- | --- |
| `bg` | `#F2E4D0` | 底色，由 3D 相机清屏给出 |
| `panel` | `#FFFCF7` | 面板，比底色更白 |
| `panelGlass` | `#FFFCF7` α235 | 叠在 3D 上的面板 |
| `panelLight` | `#F7EEE2` | 次级容器 |
| `track` | `#ECE2D4` | 进度条底槽 |
| `accent` | `#D9A05B` | 主色，焦糖橘 |
| `accentPressed` | `#C08A47` | 主色按下态 |
| `accentText` | `#FFF9F0` | 主色按钮上的文字（近白） |
| `disabled` | `#D6CBBC` | 禁用态 |
| `title` | `#4A3728` | 主标题，深棕 |
| `text` | `#6A523D` | 正文 |
| `dim` | `#9A8570` | 辅助信息 |
| `ok` | `#6BBF7B` | 成功、收益 |
| `warn` | `#E09A33` | 提醒、升级 |
| `danger` | `#D85E50` | 失败、属性告急 |

| `point` | `#8B7DBF` | 营销积分，冷紫 |

> **改配色要成对改。** 这套是浅底深字，和之前的深底浅字完全相反。
> 只换 `bg` 不换 `title`/`text`，会直接变成浅底浅字看不见。
> 代码实现在 `assets/scripts/ui/widgets.ts` 的 `COLOR`，两边必须同步。

**两种货币必须用不同颜色和图标**——游戏币和营销积分是物理隔离的两个池，
兑换目录里两种计费方式混排，颜色是玩家分辨的第一线索。

#### 稀有度配色（P8 新增）

宠物、Petpet、配饰、皮肤统一用这套分级，卡片边框取对应色：

| 稀有度 | key | 色值 | 边框粗细 |
| --- | --- | --- | --- |
| 普通 | `common` | `#7D7791` | 2px |
| 优秀 | `uncommon` | `#6DDF9C` | 2px |
| 稀有 | `rare` | `#7AC8FF` | 3px |
| 史诗 | `epic` | `#C89BFF` | 3px + 角标 |
| 传说 | `legendary` | `#FFD166` | 4px + 角标 + 常驻粒子 |

**颜色不能是唯一区分手段**——边框粗细和角标必须同步分档，
色盲玩家要能靠形状分辨。这和货币图标是同一条原则。

四条属性条各有专属色：饱食 `#E8A33D`、清洁 `#5BA3D9`、心情 `#EE8FA0`、体力 `#7CC47F`。
**任一属性低于 20% 时整条转 `danger`**，让玩家一眼看出该照顾哪项。

> 这四个色比深底方案时**加深了一档**。浅底上的高饱和亮色（原来那套）
> 对比度不够，进度条会糊在面板里看不清。

### 2.3 字号

| 层级 | 字号 | 用法 |
| --- | --- | --- |
| 大数字 | 64 | 弹窗里的奖励数值 |
| 标题 | 30 | 弹窗标题 |
| 宠物名 | 26 | 主界面 |
| 按钮 | 22–24 | |

| 辅助 | 15–17 | 属性数值、说明 |

### 2.5 动效

| 场景 | 时长 | 缓动 |
| --- | --- | --- |
| 按钮按下 | 即时（下沉 3px + 主色加深） | 无 |
| 收益飘字 | 上浮 0.9s，延迟 0.35s 后淡出 0.55s | 线性 |
| 数值强调 | 放大 0.12s → 回弹 0.18s | 默认 |
| 弹窗出现 | 1.04 倍轻弹 | 默认 |
| 宠物待机呼吸 | 1.4s 一呼一吸 | `sineInOut` |
| 宠物待机浮动 | 2.6s 一上一下 | `sineInOut` |
| 宠物互动反馈 | 压扁 0.1s → 回弹 0.22s | `quadOut` / `backOut` |

**待机动画是性价比最高的一项。** 静止的模型看着像张图，
加一点周期性起伏就有「活着」的感觉，在没有骨骼动画时尤其重要。

## 三、组件规范

### 3.1 属性条

名称在左（`dim`，15）、数值在右（`text`，15），条在下方。
体力显示 `当前 / 上限`，其余显示整数。低于 20% 时条和数值同时转 `danger`。

数值来自服务端，两次请求之间由 `core/predict` 做视觉平滑。
**本地预测只用于视觉，任何判定以服务端返回为准。**

### 3.2 操作按钮

四个等宽排一行，宽度 = `(720 - 64 - 12×3) / 4`。
主文案在上、状态在下（冷却秒数 / `…` 表示请求中）。

三种状态：可用（`accent`）、按下（`accentPressed` + 下沉 3px）、禁用（`disabled`）。
**冷却由本地倒计时驱动**，服务端 429 只作兜底。

### 3.3 弹窗

半透明黑遮罩 α170 + 居中面板，遮罩必须挂 `BlockInputEvents` 挡住底层点击。
右上角关闭按钮，主操作用胶囊按钮居中放底部。
操作完成后按钮立刻转禁用态，避免玩家以为还能再点。

### 3.4 3D 舞台

| 项 | 值 |
| --- | --- |
| 相机 | 透视，FOV 38，位置 (0, 1.75, 5.4)，俯角 9° |
| 主光 | 平行光，色温偏暖 `#FFF8EC`，照度 88000，欧拉角 (-52, -35, 0) |
| 环境光 | 天空色 `Vec4(0.95, 0.89, 0.81, 1)`，照度 **14000** |
| 地台 | 半径 2.3 的扁圆柱，`#C9AE8B` |
| 材质 | `builtin-standard`（PBR），粗糙度 0.9，金属度 0 |

**浅底方案的两条光照要点**（换成暖米白底之后调过）：

1. **环境光要压低**（22000 → 14000）。环境光一强，暗面被填平，
   模型就"塌"成一张贴纸，立体感全靠主光的明暗交界撑着。
2. **毛色要比背景深一档，地台再深一档**。浅色宠物放在浅底上会糊成一片，
   轮廓靠明度差拉开，不要靠描边。这三档明度必须拉开距离：

   | | 色值 | 明度 |
   | --- | --- | --- |
   | 背景 `bg` | `#F2E4D0` | 0.90 |
   | 宠物基准毛色 | `#D9BE96` | 0.76 |
   | 地台 | `#C9AE8B` | 0.70 |

   > 地台原为 `#DEC7A8`（明度 0.80），比背景只暗一档，毛色就没有落脚的区间了——
   > 夹在 0.80–0.90 之间的毛色等于一只浅色宠物站在浅底上，正是本条要避免的情况。
   > 2026-08-27 把地台压深到 `#C9AE8B`，占位模型实测确认过对比度。
   > 皮肤贴图整体明度都要落在毛色这一档附近，`skin_snow` 这类最浅的也不要超过 0.85。

**主光从左上前方打**，让球面有明确的明暗交界——立体感主要来自这个，不是来自模型精度。
不要用 `builtin-unlit`，那会退回平涂，3D 就白做了。

**相机分工**：3D 相机 priority 0 负责清屏、只看 `DEFAULT` 层；
UI 相机 priority 1、`DEPTH_ONLY` 只清深度、只看 `UI_2D` 层。
运行时创建的 UI 节点必须显式设 `layer = Layers.Enum.UI_2D`，
`new Node()` 默认是 `DEFAULT` 层，不设会和 3D 场景混在一起渲染。

## 四、性能预算

### 4.1 平台硬限制（微信官方文档）

这些是平台定的，不是我们自己的目标，超了就是发不出去或者跑崩。

| 项 | 限制 | 来源 |
| --- | --- | --- |
| 主包 | **≤ 4 MB** | 分包加载文档 |
| 所有包合计 | **20 MB**（开通虚拟支付后 30 MB） | 代码包文档 |
| 单个普通分包 | 不限大小 | 分包加载文档 |
| 单个独立分包 | ≤ 4 MB | 独立分包文档 |

> ⚠️ **我们的总量上限是 20 MB，不是 30 MB。**
> 30 MB 那档需要开通虚拟支付，而项目铁律是**全程不接入支付**。
> 微信文档不同页面对这个数字表述不一致（有的页面直接写 30 MB），
> **按 20 MB 规划**，等上线前找平台确认。这条差 10 MB，会直接决定能塞多少 3D 资源。

### 4.2 运行时内存

内存比包体更容易出事——超了不是加载慢，是**闪退**。

| 平台 | 低端机 | 中高端机 |
| --- | --- | --- |
| Android | < 1.2 GB | < 1.5 GB |
| iOS | **< 1 GB** | < 1.4 GB |

**iOS 低端机是最硬的那堵墙**：官方数据里 iOS 低档机型仍占约 10%–15%，
而 iOS 上小游戏和微信客户端同进程，两者加起来触到 OOM 阈值就会被系统直接杀掉。

图形内存是大头。官方给的实测对比：同一批资源用压缩纹理后，
纹理内存从 78 MB 降到 20 MB，**降幅约 70%**。

### 4.3 纹理压缩（有两个坑）

| 平台 | 可用格式 |
| --- | --- |
| iOS | ASTC、PVRTC、ETC1（仅高性能模式） |
| Android | ASTC、ETC1、ETC2 |
| 开发者工具 | DXT / BC 系列 |

**坑一：开发者工具里看到的内存数据不可信。** 工具不支持 ASTC，会回退成未压缩格式，
于是"明明做了压缩，测出来内存还是很高"。**纹理压缩效果必须以真机实测为准。**

**坑二：PVRTC 要求贴图是 2 的幂「且长宽相等」。** 不满足会被强行拉到更大的正方形——
一张 879×1242 的图转 PVRTC 后体积反而暴涨。所以**所有贴图一律做成正方形的 2 的幂**
（256×256、512×512、1024×1024）。另外开 Mipmap 会让纹理内存再涨约 33%，要权衡。

### 4.4 我们的预算

| 项 | 预算 | 当前 |
| --- | --- | --- |
| 主包 | ≤ 4 MB | **2.09 MB** |
| 分包总量 | ≤ 16 MB（20 − 4） | 0 |
| 整屏 DrawCall | ≤ 50（低端机） | 主界面约 20 |
| 同屏骨骼角色 | 1–2 只 | 占位模型无骨骼 |

**16 MB 分包能装多少？** 按本文档的规格粗算（ASTC 压缩、512² 身体贴图、256² 配饰贴图）：

| 资源 | 单个约 | 当前需求 | 小计 |
| --- | --- | --- | --- |
| 宠物网格 + 贴图 | 0.5 MB | 2（猫/狗） | 1.0 MB |
| 皮肤贴图 512² | 0.25 MB | 10 | 2.5 MB |
| 动画片段 | 0.1 MB | 8 | 0.8 MB |
| 配饰 | 0.1 MB | 7 | 0.7 MB |
| 家具 | 0.15 MB | 7 | 1.1 MB |
| 背景 1024² | 0.5 MB | 4 | 2.0 MB |
| **合计** | | | **约 8 MB** |

**结论：包体不是瓶颈，还有一倍余量。** 真正的天花板是
①主包那 4 MB（首屏必需资源要精简）②iOS 低端机内存 ③DrawCall。

按这个单价反推，16 MB 大约能容纳 **20–30 个不同的宠物形象**。
所以"做几个品种"这件事，卡住的从来不是包体，
而是美术产能和 5.1 节说的那套骨架/挂点一致性成本。

**合批要点**：Cocos 按渲染顺序合批，中间插入不同类型的组件会断批。
各界面统一「先挂完所有 Graphics、再挂所有 Label」，不要按视觉分组一块块建节点。

反面例子：自检页用 RichText 的颜色标签渲染整页文本，每个 `<color>` 片段切一次批，
一页就 128 个 DrawCall。**正式界面不要用这个偷懒写法。**

**重绘节流**：进度条这类每帧都在变的内容，先算一个「看得见的变化」签名
（数值取整、冷却取秒），没变就跳过重建网格。

## 五、宠物 3D 模型规范

宠物是全局唯一的主视觉，玩家 90% 的时间在看它。这一节的约束比其他资源都严。

### 5.1 物种：猫与狗

**只做猫、狗两种**，对应接口里的 `species` 字段（值待后端确认，见第十节）。

两个物种必须**共用一套骨架**。这是成本上的关键决定：

| 共用 | 各自独立 |
| --- | --- |
| 骨骼层级与命名 | 网格（剪影） |
| 骨骼数量与朝向 | 贴图 |
| 换装挂点位置 | — |
| **全部 8 个动画** | — |

共用骨架意味着**动画只做一套**，两个物种复用，工作量直接减半；
配饰也只做一套，猫和狗都能戴，不用出两份。
如果两边骨架不一致，动画、配饰、挂点全部要做两遍，成本翻倍还容易对不齐。

猫狗的差异**只体现在网格剪影和贴图上**：

| 部位 | 猫 | 狗 |
| --- | --- | --- |
| 耳朵 | 尖立三角 | 垂耳或半垂 |
| 脸型 | 圆脸、短吻 | 略长吻部 |
| 尾巴 | 细长上翘 | 短粗或卷曲 |
| 体态 | 纤细 | 敦实 |

同一根骨骼驱动不同网格是标准做法，美术只要保证蒙皮权重刷在同一套骨骼上即可。

**关于品种（布偶 / 橘猫 / 柯基 / 柴犬…）：接口层现在没有这个维度。**

后端只有 `species` 一个字段，玩家可换的只有 `skin_*` 五款皮肤。
如果产品要做"品种"，有三条路，成本差很多：

| 方案 | 做法 | 成本 | 后端改动 |
| --- | --- | --- | --- |
| A. 品种即皮肤 | 把 `skin_snow` 之类直接当成品种（雪白猫 / 三花猫） | 最低，已有方案 | 无，只改文案 |
| B. 品种即物种 | `species` 扩成 `cat_ragdoll` `dog_corgi` 等 | 每个品种一套网格 + 贴图 | 枚举扩容 |
| C. 品种独立字段 | 新增 `breed` 字段，与 `species`、皮肤三维正交 | 最高，组合爆炸 | 加字段、改建宠与换装接口 |

**建议先走 A**：品种只体现为花色和名字，网格仍是猫、狗各一套。
等玩法验证过、确实需要更多形象再升级到 B。
C 在这个体量的项目里不划算——三个维度相乘，美术量会失控。

这条**尚未拍板**，见第十节。

### 5.2 造型与比例

**风格参考图**：`assets/style-pet-concept.png`（2026-08-27 定稿方向）。
猫狗等高、共用比例，靠耳朵和尾巴区分。

> ⚠️ **这张图是风格方向，不是设计稿，不能直接拿去建模。**
>
> 它只有一个 3/4 视角，侧面、背面、顶面全都没有。
> 美术照着它建模，看不见的部分只能自己编——**两个人做出来会是两只不同的宠物**，
> 猫和狗的比例也对不齐，共用骨架的前提就没了。
>
> 开工前必须先补齐这三样：
>
> | 交付物 | 内容 |
> | --- | --- |
> | **三视图** | 正视、侧视、顶视，猫狗各一套，**同一比例尺、同一基准线** |
> | **色卡** | 每个部位的十六进制色值（主毛色、耳内、鼻、爪垫、眼），带标注 |
> | **细节大样** | 脸部（眼睛形状与高光位置）、耳朵、爪、尾巴末端的放大图 |
>
> 三视图的基准线尤其重要：猫和狗的**眼睛高度、颈部位置、四肢长度必须在同一水平线上**，
> 否则挂点位置对不齐，同一顶帽子在两个物种身上会一高一低。

- **风格**：Q 版三头身，低多边形 + 柔和圆润。不做写实毛发，不做次表面散射。
- **头身比**：头 : 身 ≈ 1 : 1.2，头略大于身体。养成品类靠"幼态"讨喜，头小了不可爱。
- **剪影优先**：手机屏上宠物实际显示区域只有约 300×300 逻辑像素，
  远看只剩轮廓。**耳朵、尾巴这些识别度高的部位要做夸张**，细节雕在轮廓上而不是贴图上。
  猫狗的区分度也全靠这两处，正面看头身几乎一样。
- **面部**：眼睛做成独立的球体或片面，不要靠贴图画眼睛——换皮肤时贴图会连眼睛一起换掉。

### 5.3 尺寸与坐标

| 项 | 规范 |
| --- | --- |
| 单位 | 1 Cocos 单位 = 1 米 |
| 整体高度 | **2.0 单位**（含耳朵），坐姿约 1.6 |
| 原点 | 脚底中心，即模型站在 `y = 0` 平面上 |
| 朝向 | 面朝 **+Z**，头顶朝 **+Y** |
| 缩放 | 导出时必须 **apply scale = 1**，不要靠节点缩放凑大小 |

> 相机固定在 `(0, 1.75, 5.4)`、俯角 9°、FOV 38。按这套尺寸建模，导进来就是构图正好的。
> 尺寸不对会导致每次换模型都要重调相机，多套皮肤之间还会大小不一。

**体型可以不一样，但要用「整体等比缩放」来表达。**

上面 2.0 单位是**基准尺寸**，建模时所有物种都按这个基准做，
体型差异通过一个缩放系数施加在宠物根节点上：

| 物种 | 缩放系数 | 实际高度 |
| --- | --- | --- |
| 猫 | 0.88 | 1.76 |
| 狗（基准） | 1.00 | 2.00 |

为什么这样安全：Cocos 的挂点会把骨骼的**完整世界矩阵（含缩放）**写给挂载节点，
所以宠物整体缩小时，帽子、围巾会跟着等比缩小，位置和大小自动正确，
**不需要为每个物种出一套配饰**。这一点我在引擎源码里确认过
（`cocos/3d/skeletal-animation/skeletal-animation.ts`，socket 更新时直接赋 `target.matrix`）。

会出问题的是**非等比的比例改动**，主要是头身比：

- 帽子是挂在头骨上的，尺寸按头部大小设计。
- 如果猫的头相对身体明显更大（只改网格、不改骨骼缩放），
  挂点的位置和缩放不变，同一顶帽子在大头上就显小。
- 所以 **头身比要控制在窄区间**：各物种头部体积差异不超过 ±10%，
  超出这个范围就得为该物种单独出配饰。

**取值范围建议控制在 0.85–1.15。** 相机是固定的，
缩得太小宠物在屏幕上会显得又远又小，主视觉就塌了；
差异感靠剪影和胖瘦来表达比靠尺寸更有效。

### 5.4 面数与骨骼预算

| 项 | 预算 | 依据 |
| --- | --- | --- |
| 三角面 | **≤ 3000** | 同屏只有 1 只，低端机整屏三角面留足余量 |
| 骨骼数 | **≤ 30 根**（标准骨架 28 根） | 硬限制，见下方说明 |
| 材质球 | **≤ 2** | 每个材质一个 DrawCall |
| 子网格 | ≤ 3 | 但耳朵、颈部必须独立，见 5.5 遮挡规则 |

**骨骼 30 根是硬线，不是建议。** Cocos 的实时蒙皮走 uniform 传骨骼矩阵，
容量常量 `JOINT_UNIFORM_CAPACITY = 30`（`cocos/rendering/define.ts`）。
一旦超过，引擎会自动退化成**贴图蒙皮**模式——需要浮点纹理支持，
低端机和部分微信环境上性能明显下降，还可能直接不支持。

**换装必须关预烘焙动画。** 项目规则要求 3D 换装走实时蒙皮
（`SkeletalAnimation.useBakedAnimation = false`），预烘焙模式下骨骼矩阵被烤进贴图，
配饰无法跟着骨骼走。这也意味着骨骼预算不能超，否则实时蒙皮的代价会翻倍。

#### 标准骨架（**必须严格照此实现**）

这是整个美术流程里**唯一不能返工**的东西：16 个动画和 7 件配饰全部绑在它上面，
骨架一改（加骨头、改名字、改层级）就要全部重做。
所以**先按这份清单做出骨架、双方确认，再动手做动画**。

猫狗**共用这一套**，28 根骨骼，在 30 上限内留了 2 根余量：

```
root                        1   世界原点，脚底中心，不参与蒙皮
└ hips                      2   胯，动作的重心
  ├ spine_01                3
  │ └ spine_02              4
  │   ├ neck                5
  │   │ ├ socket_neck       6   ★ 不蒙皮，挂围巾/领巾/铃铛
  │   │ └ head              7
  │   │   ├ ear_L           8
  │   │   ├ ear_R           9
  │   │   ├ jaw            10   下颌，吃东西/说话
  │   │   └ socket_hat     11   ★ 不蒙皮，挂帽子/皇冠/墨镜
  │   ├ shoulder_L         12
  │   │ └ leg_front_L_01   13
  │   │   └ leg_front_L_02 14
  │   │     └ paw_front_L  15
  │   └ shoulder_R         16
  │     └ leg_front_R_01   17
  │       └ leg_front_R_02 18
  │         └ paw_front_R  19
  ├ leg_back_L_01          20
  │ └ leg_back_L_02        21
  │   └ paw_back_L         22
  ├ leg_back_R_01          23
  │ └ leg_back_R_02        24
  │   └ paw_back_R         25
  └ tail_01                26
    └ tail_02              27
      └ tail_03            28
```

**预留的 2 根余量不要随意用掉**——将来如果发现某个动作缺关节（比如跳舞需要
额外的脊椎段），还有腾挪空间。用满 30 根就没有退路了。

#### 命名规范

| 规则 | 说明 |
| --- | --- |
| 全小写 + 下划线 | `leg_front_L_01`，**不能用中文、空格、点号** |
| 左右后缀用 `_L` / `_R` | 大写，方便镜像工具识别 |
| 链式关节用 `_01` `_02` 编号 | 从靠近身体的一端开始数 |
| 挂点一律 `socket_` 前缀 | 前端按名字查找，**拼错就是静默挂不上** |

**命名必须逐字一致。** 前端和动画系统都按字符串查找骨骼，
`leg_front_l_01`（小写 l）和 `leg_front_L_01` 是两根不同的骨头。

#### 轴向与绑定姿势

| 项 | 约定 |
| --- | --- |
| 模型朝向 | 面朝 **+Z**，头顶 **+Y**（与 5.3 一致） |
| 骨骼朝向 | 每根骨头的 **+Y 指向子骨头**，无子骨头的沿用父骨头朝向 |
| 绑定姿势 | **四足自然站立**：四肢垂直地面、头平视前方、尾巴自然下垂 |
| 骨骼缩放 | 全部为 1，**不要用骨骼缩放去调体型**（体型走根节点整体缩放，见 5.3） |

> 四足动物**不用 T-pose**。T-pose 是两足角色的惯例，四足摆成 T 字没有意义，
> 自然站立姿势更利于刷权重和做动画。

#### 挂点骨骼的特殊要求

`socket_hat` 和 `socket_neck` 是两根**不蒙皮**的骨头——
没有任何网格顶点绑定到它们，只用来定位。

| 项 | 要求 |
| --- | --- |
| 位置 | `socket_hat` 在头顶正中；`socket_neck` 在颈部下缘正中 |
| 局部坐标 | **+Y 朝外**（远离身体），+Z 朝前 |
| 跟随 | 必须是 `head` / `neck` 的子骨头，跟着一起动 |
| 猫狗一致 | 两个物种的挂点**相对位置必须相同**，否则同一顶帽子会一个正好一个歪 |

配饰按同样的朝向建模，导入后直接挂上就位置正确，不需要前端逐件调偏移。

#### 交付验收清单

美术交付骨架时，按这几条自查，任何一条不过都要退回重做：

- [ ] 骨骼总数 ≤ 30（当前标准为 28）
- [ ] 骨骼名与上方清单**逐字一致**，无中文无空格
- [ ] 层级关系与上方树形图一致
- [ ] `socket_hat` / `socket_neck` 存在，且**无蒙皮权重**
- [ ] 所有骨骼缩放为 1，无负缩放
- [ ] 绑定姿势为四足自然站立
- [ ] 模型面朝 +Z，原点在脚底中心
- [ ] 猫、狗两个网格绑在**同一套骨架**上，骨骼名与层级完全相同
- [ ] 导出前已清理摄像机、灯光、辅助物体、约束、IK 控制器

> **IK 控制器不要导出。** 绑定时用 IK 方便摆姿势，但导出的动画应该是烘焙到
> FK 骨骼上的关键帧。带 IK 节点导进引擎会变成多余骨骼，白白占用 30 根的预算。

#### 蒙皮权重

**这是最容易出问题、又最难返工的一环。** 权重刷坏了，
要等动画做完、模型动起来才看得出关节塌陷，那时候改就得连动画一起重做。

| 项 | 规范 |
| --- | --- |
| 每顶点最大骨骼数 | **4 根**（引擎 shader 是 `a_weights` vec4，超出的会被丢弃） |
| 权重归一化 | 每个顶点的权重之和 **必须等于 1** |
| 挂点骨骼 | `socket_hat` / `socket_neck` 权重必须为 **0**，一个顶点都不能绑 |
| 关节布线 | 每个弯曲关节处至少 **2–3 圈环形布线**，否则一弯就塌 |

**分部位的权重要求**：

| 部位 | 要求 |
| --- | --- |
| 四肢关节 | 关节两侧渐变过渡，不要硬切；膝/肘弯到 90° 不能出现凹陷 |
| 颈部 | 头与躯干之间平滑过渡，头左右转 45° 时颈部不能出现折痕 |
| 耳朵 | 耳根渐变、耳尖 100% 绑对应耳骨；**不能被头部骨骼污染**，否则耳朵会跟着脸变形 |
| 尾巴 | 三段骨骼依次渐变，摆动时是连续曲线而不是三节棍 |
| 下颌 `jaw` | 只影响下颌和舌头，**不能影响到眼睛和耳朵** |

**最常见的错误是"权重溢出"**——某根骨头影响到了不相干的部位，
比如尾巴骨骼上残留了后腿的权重，尾巴一摆腿就跟着抽。
刷完权重后逐根骨骼单独旋转到极限角度检查，是唯一可靠的排查方法。

#### 网格与法线

| 项 | 规范 |
| --- | --- |
| 法线朝向 | **一律朝外**。翻转的面在引擎里会变黑或直接不可见 |
| 双面材质 | **不用**。双面渲染会翻倍 overdraw，移动端代价高 |
| 薄片结构 | 耳朵、舌头这类要做**有厚度的实体**，不要用单面片——单面片背面会消失 |
| 封闭性 | 模型必须是封闭的，不要有裸露的洞（相机会转到侧面） |
| 硬边软边 | 靠平滑组控制；**硬边处 UV 必须断开**，否则会出现明显的法线接缝 |
| 独立子网格 | 耳朵、颈部必须是独立节点（`part_ears` / `part_neck`），见 5.5 遮挡规则 |
| N-gon | 不允许。全部三角形或四边形 |

### 5.5 换装挂点

配饰不是合进模型的，是运行时按 `slot` 挂到骨骼上的。**模型必须预留这些空骨骼**：

| slot | 挂点骨骼名 | 位置 |
| --- | --- | --- |
| `hat` | `socket_hat` | 头顶正中，Y 轴朝上 |
| `neck` | `socket_neck` | 颈部下缘正中 |

- 挂点骨骼**不蒙皮**，只做定位，但要跟随头/颈骨骼变换。
- 挂点的局部坐标系：+Y 朝外（远离身体），+Z 朝前，配饰按同一朝向建模即可直接挂上。
- 命名必须严格一致，前端按名字查找，拼错就是静默挂不上。
- **各物种的挂点名称、以及挂点在骨架上的相对位置必须一致**（归一化到基准尺寸后）。
  整体等比缩放不影响——缩放会跟着世界矩阵传给配饰；
  但如果挂点在头上的相对位置变了（比如狗吻部拉长导致颈部挂点前移），
  同一条围巾就会一个正好一个歪，那就得出两套。

`body`（皮肤）和 `bg`（背景）不用挂点：皮肤是换贴图，背景是换场景。

#### 行业做法参考

同类问题（物种 / 品种 / 换装怎么组织）主要有三种成熟路线，各自的取舍很不一样：

| 游戏 | 做法 | 品种怎么表达 | 配饰怎么兼容 |
| --- | --- | --- | --- |
| **Neopets** | 2D 分层贴图 | 物种 × 颜色 | **体型 ID** 兼容表 |
| **模拟人生 4：猫狗** | 3D 蒙皮 + 形变 | **同一套骨架上的形变参数** | 服装蒙皮到同一骨架，跟着形变自动适配 |
| **Adopt Me!（Roblox）** | 每只宠物独立模型 | **不做品种**，每只宠物是独立收集品 | 基本不做换装，靠稀有度和融合形态制造深度 |

**模拟人生 4 那条最值得看**，因为它和我们的场景几乎一样——就是猫和狗。
它有 **123 个狗品种 + 49 个猫品种**，但**并没有为每个品种做独立骨架**：

> pets function on standardized rigs that the game uses to handle movement and animations；
> 自定义宠物服装必须蒙皮到对应的 rig 上才能正确形变和播动画。

也就是说，170 多个品种全部跑在**每个物种一套的标准骨架**上，
品种差异是骨架上的**形变参数 + 毛色贴图**，服装蒙皮到同一骨架、跟着体型形变走。

这直接验证了我们"猫狗共用骨架、品种不新开骨架"的方向是对的。
差别在于模拟人生用了形变（morph）来做连续的体型变化，
而形变会增加顶点数据量——**在 4MB 主包的微信小游戏里不划算**，
所以我们不做形变，品种走离散的皮肤方案（5.1 节方案 A）。

**Adopt Me! 是另一条完全不同的路**：它压根不做品种和换装，
每只宠物就是一个独立收集品，靠稀有度分级（普通到传奇）、孵化概率、
以及"四只成年宠物融合成霓虹形态"来制造收集深度。

这条路和我们已有的**扭蛋 + 图鉴**系统其实很契合，可以作为后续扩展方向：
与其做"猫的十个品种"，不如把新形象直接做成扭蛋奖池里的稀有收集品。
不过那属于玩法设计范畴，得产品来定。

#### 遮挡规则：戴上配饰要藏起哪些部位

配饰不只是"挂上去"，还得处理**穿模**：帽子扣在头上，尖立的猫耳会戳出来；
围巾绕在脖子上，颈部的毛会穿出来。

Neopets 的换装系统把这件事抽象成一条规则，值得直接借鉴：

> Restrictions are subtractive：先假定所有部位都显示，再按规则隐藏一部分。

落到我们的模型上，**每件配饰要声明它会遮住宠物的哪些部位**：

| 配饰 | 建议隐藏 |
| --- | --- |
| `acc_cap` 棒球帽 | 耳朵（或改用贴合帽型的耳朵变体） |
| `acc_crown` 小皇冠 | 无（架在头顶上方，不冲突） |
| `acc_scarf` 围巾 | 颈部 |
| `acc_bandana` 领巾 | 颈部 |

具体做法：宠物模型把**耳朵、颈部做成独立的子网格节点**，
前端按配饰的遮挡声明去 `active = false`。所以美术这边要保证：

- 耳朵、颈部**不能和身体合成一个网格**，否则没法单独隐藏。
- 节点命名固定：`part_ears`、`part_neck`，和挂点一样，拼错就是静默失效。

遮挡关系目前**硬编码在前端**（配饰数量少，7 件）。
如果将来配饰变多、或者运营要频繁调整，再考虑让后端在 `WardrobeItem` 上带一个
`hides` 字段——但现在没必要，加了反而是过度设计。

#### 体型 ID：配饰兼容性的正确判据

**不要用「物种」或「品种」去判断一件配饰能不能戴，要用「体型 ID」。**

这是 Neopets 的换装系统（Dress to Impress）跑了二十年验证出来的做法，
它有 50 多个物种、几百种颜色，靠的就是这一个字段。它的架构文档里写得很直接：

> body_id is the compatibility key, not species or color.
> "Blue Acara" 和 "Red Acara" 共用同一个 body_id（形状相同），
> 但 "Maraquan Acara" 的 body_id 不同（形状不同）。

翻译到我们这里：

| 情况 | 体型 ID | 配饰 |
| --- | --- | --- |
| 猫、狗（共用骨架、等比缩放、头身比接近） | **同一个** | 全通用 |
| 换皮肤（只换贴图，不改形状） | 不变 | 不受影响 |
| 将来出体型特殊的品种（比如腊肠犬那种拉长身体） | **新开一个** | 需要专属配饰 |

这样做的好处是**判断依据和内容形态解耦**：
运营新增一个品种时，只要它沿用现有体型，配饰立刻全部可用，一件都不用补；
只有真正改了体型的才需要额外投入，而且投入范围一眼可算。

如果按「物种」判断，就会出现"新加一个物种，所有配饰都要重新确认一遍"的窘境；
按「品种」判断则更碎。**体型 ID 是唯一稳定的那个维度。**

**现阶段我们只有一个体型 ID**（猫狗共用），所以前端先不引入这个字段，
按"配饰全通用"实现。但**美术和后端都要知道这条约束的存在**：
一旦有人提出"做一只腊肠犬"，就要同时意识到那是新体型、要配套出配饰，
而不是以为换个模型就完事。真到那一步，接口需要加 `bodyId`（见《后端配合需求清单》3.7）。

> 顺带说明为什么我们用「离散体型 ID」而不是模拟人生那种「连续形变」：
> 形变要为每个体型存一套顶点偏移数据，服装也要跟着蒙皮形变。
> 在 4MB 主包 + 低端机 DrawCall ≤ 50 的约束下，这个代价换不回对应的体验提升。
> 离散体型 ID 的好处是**成本可预测**——加一个新体型的代价是明确的、可以提前算出来的。

### 5.6 动画列表

**所有动画猫狗共用，只做一套。** 绑在共用骨架上，两个物种都能播。
统一 **30 FPS**，循环动画首尾帧必须一致（否则会有跳帧）。

按优先级分三批交付，**第一批做完就能上线**。

#### 第一批 · 基础（8 个，P0–P1 需要）

| 动画名 | 时长 | 循环 | 触发 |
| --- | --- | --- | --- |
| `idle` | 2.0–3.0s | 是 | 默认状态，必须自然、幅度小 |
| `idle_hungry` | 2.0–3.0s | 是 | 饱食 ≤ 20，蔫一点 |
| `idle_sick` | 2.0–3.0s | 是 | 患病时（P1），比 hungry 更蔫、偶尔抖一下 |
| `feed` | 1.5–2.0s | 否 | 点喂食 |
| `bath` | 1.5–2.0s | 否 | 点洗澡 |
| `pet` | 1.0–1.5s | 否 | 点抚摸，蹭一下 |
| `play` | 1.5–2.5s | 否 | 点陪玩，动作最大 |
| `happy` | 1.0–1.5s | 否 | 升级、领奖、融合成功 |

#### 第二批 · 性格变体（3 个，P10 需要）

性格特质有六种，但**不需要做六套 idle**。
差异最大的三种单独做，其余用**播放参数**（速度、幅度）在同一个 `idle` 上调出来。

| 动画名 | 对应特质 | 表现 |
| --- | --- | --- |
| `idle_lively` | 活泼 | 幅度大、常小跳、左右张望 |
| `idle_timid` | 胆小 | 幅度极小、偶尔缩一下、耳朵后压 |
| `idle_lazy` | 嗜睡 | 趴着，呼吸慢 |

其余三种的处理：贪吃 = `idle` 播放速度 1.05 + 偶尔插 `feed` 的前半段；
高冷 = `idle` 但角色朝向偏转 30°；爱干净 = `idle` 偶尔插一段舔毛（可并入 `idle` 本身的长循环）。

#### 第三批 · 训练技巧（5 个，P13 需要）

| 动画名 | 时长 | 循环 | 解锁等级 |
| --- | --- | --- | --- |
| `trick_sit` | 1.0–1.5s | 否 | Lv1 |
| `trick_shake` | 1.0–1.5s | 否 | Lv5 |
| `trick_roll` | 1.5–2.0s | 否 | Lv10 |
| `trick_jump` | 1.5–2.0s | 否 | Lv20 |
| `trick_dance` | 2.5–3.5s | 是 | Lv30 |

技巧动画会按**熟练度**调整播放：熟练度低时速度 0.85、幅度 0.8（动作生涩），
满熟练度时速度 1.0、幅度 1.0（动作流畅）。**美术只做满熟练度的版本**，
生疏感由前端调参实现。

#### 通用规则

- **`idle` 优先级最高**，其他没做完也能先上线，前端会退回 `idle`。
- 单次动画播完自动回 `idle`，美术不需要做过渡帧，引擎做混合。
- 幅度控制：`idle` 是玩家看最久的，**幅度过大会让人烦躁**，参考呼吸起伏 3% 左右。
- `sleep` 已从清单移除——离线返回时用 `idle_lazy` 代替，省一个动画。

**合计 16 个动画**（8 基础 + 3 性格 + 5 技巧）。

### 5.7 成长阶段与形态

宠物有两个正交的外观维度，**都不需要新模型**。

#### 成长阶段（P0）

`stage` 字段由服务端下发，前端按阶段缩放宠物根节点：

| stage | 等级 | 缩放 | 额外表现 |
| --- | --- | --- | --- |
| `baby` | 1–5 | 0.72 | `idle` 播放速度 ×1.15（幼崽动作更碎更快） |
| `teen` | 6–15 | 0.86 | — |
| `adult` | 16–100 | 1.00 | — |

**美术只需按 `adult` 基准建模**，幼年和少年由缩放得到。
配饰会跟着挂点的世界矩阵自动缩放，不用出小号配饰。

> 如果要更讲究，可以为 `baby` 额外出一套头身比更夸张的网格（头更大、腿更短）。
> 但那是锦上添花，**不做也能上线**，优先级低于第三批动画。

#### 融合形态（P8）

| form | 表现 | 实现 |
| --- | --- | --- |
| `normal` | 常规 | 标准 PBR 材质 |
| `glow` 辉光 | 自发光 + 缓慢呼吸光效 | **同一网格**，材质开 emissive，强度做正弦起伏 |
| `rainbow` 虹彩 | 自发光 + 色相循环 + 常驻粒子 | 同上 + emissive 色相随时间循环 + 粒子 |

**这两个形态不需要任何新模型和新贴图**——沿用现有网格，
只改材质参数、加一个粒子。这是全部美术需求里性价比最高的一项，
视觉冲击强但成本几乎为零。

美术需要提供的只有：粒子贴图 1 张（64×64 光点）+ 两种形态的效果参考图。

### 5.8 贴图与材质

| 项 | 规范 |
| --- | --- |
| 贴图尺寸 | 身体 **512×512**，配饰 256×256，**一律正方形且为 2 的幂** |
| 通道 | BaseColor 必需；Normal / Metallic-Roughness 可选，能省则省 |
| 格式 | 交付 PNG，构建时由引擎转压缩纹理 |
| 材质 | `builtin-standard`（PBR），粗糙度 0.85–0.95，金属度 0 |
| UV | 单套 UV，不重叠，留 4px 边距防压缩渗色（详见下方） |

- **不要烘焙光照到贴图里。** 场景是实时光照，烤死的明暗会和实时光打架。
- **不要用 unlit 风格的平涂贴图。** 立体感来自光照，平涂会把 3D 做成 2D。
- 同一物种的五款皮肤共用同一套 UV 和网格，**只换 BaseColor 贴图**，换装零成本。

**皮肤要按物种各出一套。** 猫和狗虽然共用骨架，但网格不同、UV 也不同，
一张贴图不可能同时贴合两个模型。所以 5 款皮肤 × 2 个物种 = **10 张贴图**：

```
skin_default_cat.png    skin_default_dog.png
skin_snow_cat.png       skin_snow_dog.png
skin_tiger_cat.png      skin_tiger_dog.png
skin_calico_cat.png     skin_calico_dog.png
skin_shadow_cat.png     skin_shadow_dog.png
```

前端按 `skin_{itemKey去前缀}_{species}.png` 拼路径，商店仍然是一份列表，
后端不用改接口，运营上新皮肤前端也不用发版。

#### UV 规范（决定了 10 张皮肤能不能共用一套网格）

| 项 | 规范 |
| --- | --- |
| UV 套数 | **1 套**，不用第二套 lightmap UV（我们是实时光照，不烘焙） |
| 范围 | 全部在 0–1 空间内，不允许超出或平铺 |
| 重叠 | **不允许任何重叠**，包括左右对称部分 |
| 边距 | 每个 UV 壳之间留 **≥4 像素**（512 贴图下约 0.008 UV 单位） |
| **密度一致** | 全身 texel density 均匀，头部可适当提高但不超过 1.5 倍 |
| 硬边 | 硬边处 UV 必须断开 |

**为什么不许镜像重叠**：把左右两半 UV 叠在一起能省一半贴图空间，是常见优化。
但那样**左右花纹会强制对称**——三花、虎纹这类不对称花色做出来会很假，
而我们有 10 张皮肤贴图全靠这套 UV。这一条省不得。

**为什么密度要一致**：密度不均会导致同一张贴图上，
有的部位清晰、有的部位糊。最容易出问题的是脸部和身体的比例——
脸只占身体面积的 1/5，但玩家 80% 的注意力在脸上，
所以脸可以适当提高密度，但**不要超过 1.5 倍**，否则接缝处的清晰度落差会很明显。

**UV 壳的划分建议**：头（含耳）、躯干、四肢、尾巴分开，
接缝藏在颈部下方、四肢内侧、尾巴根部这些看不到的地方。

> **命名有个语义问题要提一句**：`skin_tiger`（虎纹）、`skin_calico`（三花）
> 是猫的花色叫法，做成狗有点别扭（虎纹可以理解成虎斑犬，三花就比较勉强）。
> 美术按"同名花色的两种诠释"处理即可，
> 如果运营觉得违和，可以考虑改成物种中性的名字——但那要后端改配置，见第十节。

## 六、图标与 2D 资源规范

### 6.1 图标通用规范

| 项 | 规范 |
| --- | --- |
| 画布 | **128×128**（@2x 出 256×256） |
| 安全区 | 四边各留 **10px** 内边距，图形主体控制在 108×108 内 |
| 风格 | **面性图标**（实心块面），不用线性描边图标 |
| 描边 | 如需描边，统一 **4px 外描边**，颜色取图标主色加深 20% |
| 圆角 | 图形内部转角 ≥ 6px，不要尖角 |
| 视觉重量 | 各图标的**视觉面积要接近**，不能一个撑满一个很小 |
| 格式 | PNG-32，带 alpha，不预乘 |
| 交付 | 单张散图交付，前端合图，**美术不要自己拼图集** |

**为什么用面性而不是线性**：图标在按钮上实际显示只有 40–48px，
线性图标在这个尺寸下会糊成一团，面性图标的剪影更清晰。

**为什么不要自己拼图集**：合图要和渲染顺序配合才能减 DrawCall，
由前端按界面分组合，美术自己拼反而会拆散合批。

### 6.2 互动图标（P0）

四个一组，必须是**同一套视觉语言**——同样的透视角度、同样的描边粗细、同样的配色饱和度。
这四个图标并排出现在主界面最显眼的位置，任何一个不统一都会很扎眼。

| itemKey | 名称 | 建议元素 |
| --- | --- | --- |
| `feed` | 喂食 | 食盆 / 骨头 |
| `bath` | 洗澡 | 泡泡 / 水滴 |
| `pet` | 抚摸 | 手掌 / 爱心 |
| `play` | 陪玩 | 球 / 飞盘 |

图标放在按钮上层、文字上方，尺寸 48×48。按钮底色是主色 `#FF9F6B`，
**图标本身用深色 `#2A1D16`**，不要用白色（在暖橙底上对比不足）。

### 6.3 货币图标（P1）

| 用途 | 建议 | 颜色 |
| --- | --- | --- |
| 游戏币 | 圆形硬币 | `#FFD166` |
| 营销积分 | 星形 / 多边形 | `#9DB2FF` |

**形状必须不同，不能只靠颜色区分。** 这两个池物理隔离、永不互转，
兑换目录里两种计费方式混排，玩家分辨错就会投诉。色盲玩家也要能分清。
尺寸 48×48。

### 6.4 消耗品图标（P2）

`cons_toy` `cons_snack` `cons_bubble` `cons_energy` `cons_cake`，
规格同通用规范，128×128。这些在商店列表里网格排列，**视觉重量一致性尤其重要**。

### 6.5 场景背景（P1）

| itemKey | 名称 |
| --- | --- |
| `bg_room` | 暖阳小屋 |
| `bg_garden` | 午后花园 |
| `bg_beach` | 海边夕照 |
| `bg_starry` | 星夜露台 |

- 尺寸 **1024×1024**，正方形且为 2 的幂。
  竖屏是 9:16，正方形图会被裁掉上下——所以**构图要按"中间那块 9:16 是安全区"来画**，
  四周留出会被裁掉的余量。
- 格式交付 PNG，构建时转 ASTC。
- **中间区域要留空**：宠物站在画面中央偏下，背景中心不要放视觉重点。
- **整体压暗、降饱和**：背景抢过宠物就本末倒置了。参考"虚化的远景"。
- 底部 1/3 会被 UI 面板压住，不要在那里放关键元素。

> 为什么不用 1080×1920 这种"看起来正好"的尺寸：iOS 的 PVRTC 压缩要求
> **正方形且 2 的幂**，非标尺寸会被强行拉大，体积和内存反而暴涨（见 4.3）。
> 宁可按正方形出图再靠构图适配，也不要出非标尺寸。

## 七、家具、配饰与 Petpet 模型规范

复用第五节的通用约束（单位、朝向、PBR 材质、不烘焙光照），差异如下：

| 项 | 配饰 | 家具 | **Petpet** |
| --- | --- | --- | --- |
| 三角面 | ≤ 400 | ≤ 800 | **≤ 300** |
| 贴图 | 256×256 | 256×256 | **128×128** |
| 材质球 | 1 | 1 | 1 |
| 骨骼 | 无（刚体挂载） | 无 | 无 |
| 原点 | 挂点接触面中心 | 底面中心 | 底面中心 |

### 7.1 Petpet（P2 新增）

宠物的宠物，一只小挂件跟在主宠脚边。**不挂骨骼挂点**，
直接放在宠物根节点下的固定偏移位置（约 `(0.55, 0, 0.3)`），
会跟着成长阶段和融合形态一起缩放。

| itemKey | 名称 | 稀有度 |
| --- | --- | --- |
| `pp_bird` | 小鸟 | 普通 |
| `pp_fish` | 小鱼 | 优秀 |
| `pp_bug` | 瓢虫 | 稀有 |
| `pp_ghost` | 小幽灵 | 史诗 |

- 高度控制在 **0.4 单位以内**，不能抢主宠的视觉。
- 各自带一个**简单的循环浮动**（不需要骨骼动画，前端用 tween 做上下浮动即可）。
- `pp_ghost` 需要半透材质 + 微弱自发光。

**家具按占格建模。** 后端给的 `gridW × gridH` 是房间网格的占格数，
房间是 6×6。**1 格 = 0.6 单位**，所以 2×1 的沙发实际尺寸是 1.2 × 0.6 单位。
超出占格会和相邻家具穿模——碰撞是按格子判的，不是按模型包围盒。

| itemKey | 名称 | 占格 | 实际尺寸（单位） |
| --- | --- | --- | --- |
| `furn_bowl` | 食盆 | 1×1 | 0.6 × 0.6 |
| `furn_mat` | 暖垫 | 2×2 | 1.2 × 1.2 |
| `furn_lamp` | 落地灯 | 1×1 | 0.6 × 0.6 |
| `furn_rug` | 圆形地毯 | 2×2 | 1.2 × 1.2 |
| `furn_sofa` | 沙发 | 2×1 | 1.2 × 0.6 |
| `furn_tree` | 猫爬架 | 1×2 | 0.6 × 1.2 |
| `furn_window` | 落地窗 | 1×2 | 0.6 × 1.2 |

高度不受格子约束，但**落地灯、猫爬架、落地窗这类高家具不要超过 1.5 单位**，
否则会挡住宠物。

配饰清单：`acc_cap` `acc_bow` `acc_glasses`（挂 `hat`）、
`acc_bell` `acc_bandana` `acc_scarf`（挂 `neck`）、`acc_crown`（挂 `hat`）。

> 换装是**纯外观**，不影响任何属性——速度和耐力只由等级决定。
> 美术不需要为不同皮肤/配饰做数值差异化的表现。

## 八、命名与交付

### 8.1 命名规则

**一律使用后端返回的 `itemKey` 作为文件名**，不要自创中文名或编号。

```
pet_default.fbx           宠物模型
pet_default_idle.fbx      动画（若拆文件）
skin_snow.png             皮肤贴图
acc_cap.fbx               配饰模型
acc_cap.png               配饰贴图
furn_sofa.fbx             家具模型
cons_snack.png            消耗品图标
bg_beach.jpg              背景
icon_feed.png             互动图标
icon_coin.png             货币图标
```

这样做的意义：**运营在后台新增一件商品，前端不用发版**。
后端返回一个新的 `itemKey`，前端按名字去加载对应资源即可。
命名对不上就得改代码，等于每次上新都要走一遍发版流程。

### 8.2 交付要求

- 源文件（.blend / .max / .psd）和导出件分开交付，源文件要留。
- 贴图与模型分离，不要嵌进 FBX。
- 每次交付附一张**效果参考图**，说明模型在游戏里应该长什么样。

### 8.3 分阶段验收

**不要等全做完再一次验收。** 骨架、模型、权重、动画是层层依赖的，
前一环出问题后面全废。每一环做完就验，验过再往下走。

| 阶段 | 验收内容 | 验收方 | 不过的代价 |
| --- | --- | --- | --- |
| ① 三视图 + 色卡 | 比例、猫狗基准线对齐、色值标注齐全 | 产品 + 前端 | 低，改图 |
| ② 骨架 | 28 根清单、命名、层级、挂点、绑定姿势 | 前端 | **极高，后面全废** |
| ③ 模型 | 面数、法线、封闭性、独立子网格、UV | 前端 | 高，要重拓扑 |
| ④ 权重 | 逐骨骼极限角度测试，无塌陷无溢出 | 美术负责人 + 前端 | **高，动画要重做** |
| ⑤ 动画 | 时长、循环首尾帧、幅度、命名 | 产品 + 前端 | 中 |
| ⑥ 贴图 | 尺寸、正方形 2 的幂、密度、无渗色 | 前端 | 低，重导 |

**② 骨架这一环最关键。** 它过了才能开始做权重和动画，
不过就必须停下来改——**这时候停的代价是最小的**。

### 8.4 怎么验

**工具**：Cocos Creator 导入后看资源检查面板（面数、骨骼数、子网格），
配合 Blender / 3ds Max 检查法线、UV、权重。

**通用检查清单**（骨架部分见 5.4 末尾的专项清单）：

- [ ] 面数、骨骼数、材质球数在预算内
- [ ] 贴图正方形且为 2 的幂
- [ ] 法线全部朝外，无翻转面
- [ ] UV 在 0–1 内、无重叠、密度均匀
- [ ] 逐根骨骼旋转到极限角度，无塌陷、无权重溢出
- [ ] `socket_*` 骨骼权重为 0
- [ ] `part_ears` / `part_neck` 是独立节点，可单独隐藏
- [ ] 导入 Cocos 后能正常播放全部动画，无报错
- [ ] 挂一件配饰上去，位置正确、不穿模

**不合格怎么处理**：退回时**必须附具体不通过项和复现方式**，
不要只说"感觉不对"。比如「`leg_back_L_02` 旋转 -80° 时膝盖内侧塌陷」
比「腿的权重有问题」有用得多。

**真机验证**：纹理压缩效果和内存**必须真机测**，
开发者工具不支持 ASTC 会回退成未压缩格式，数据不可信（见 4.3）。

### 8.5 分包策略

按项目规则，**主包 ≤ 4 MB，3D 资源一律走 Asset Bundle 远程加载**，
不进主包。当前主包 2.09 MB，留给首屏必需资源的余量不到 2 MB。

| 资源 | 归属 |
| --- | --- |
| 互动图标、货币图标、UI 元素 | 主包 |
| 宠物模型 + `idle` 动画 | 主包或首个远程包（首屏要用） |
| 其余动画、皮肤、配饰、家具、背景 | 远程 Asset Bundle |

远程资源需要一个配进微信 `downloadFile` 合法域名的地址，且支持 CORS。

### 需要后端回复的（已同步进《后端配合需求清单》）

物种定为猫、狗之后，接口层有三个问题必须先明确，否则前端没法按 `species` 取资源：

1. **`species` 的枚举值是什么？** 现在 `/pet/state` 返回的是 `"default"`。
   前端建议用 `"cat"` / `"dog"`，需要后端确认并给出完整取值范围。
2. **新玩家怎么选物种？** 对接文档写明 `/pet/state` 在玩家没有宠物时会**自动建一只**。
   如果产品上要让玩家在新手引导里选猫还是狗，那这个自动建宠会抢先建出一只 `default`，
   选择就没意义了。需要确认：是自动建宠后允许改物种，还是新手流程改成先调 `/pet/create`。
3. **换装商店要不要按物种过滤？** `GET /wardrobe` 现在返回一份全局列表，不带物种信息。
   皮肤前端可以按 `species` 拼贴图路径解决，但如果将来出「猫专属配饰」，
   接口就需要加物种字段或做过滤。现阶段按"配饰全通用"实现。

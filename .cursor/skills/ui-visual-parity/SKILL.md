# UI 视觉对标：先量，再改

「感觉不如竞品」几乎总能落到**具体数值**上。凭感觉调会来回摆 ——
本项目在墙占比上连查三轮方向都错，配色上还发生过**过度修正**
（治好塑料感却调成灰扑扑）。

## 铁律

1. **先量再改。** 用户说「不好看」时，第一步是跑脚本量两张图，不是改代码。
2. **自动判据失败两次就改用人工读坐标。** 扫白色会扫到浴缸、扫饱和度会扫到
   壁龛内部 —— 一次性对比直接从图上读像素框更快更准。
3. **公式错了，自查就成了自我欺骗。** 见下面「墙占比」那条。
4. **每次改完必须重量。** 静态推算通过 ≠ 运行时正确。

## 工作流

```
- [ ] 1. 转格式：竞品截图多是 jpg，pngjs 读不了
- [ ] 2. 量两张图，列出差距表
- [ ] 3. 定位根因（先查下面「五个已知根因」）
- [ ] 4. 改代码
- [ ] 5. 重新截图（**绝对路径**）+ 重量，确认数值真的动了
```

### 1. 转格式

```bash
cd .build && node scripts/jpg2png.mjs <竞品.jpg> cmp/rival.png
```

### 2. 量

```bash
cd .build
node scripts/color-compare.mjs cmp/rival.png shots/now.png   # 配色
node scripts/wall-ratio.mjs 竞品 cmp/rival.png 我们 shots/now.png  # 墙地占比
```

### 5. 截图必须用绝对路径

```bash
cd .build && node scripts/shot-now.mjs 'C:\...\.build\shots\now.png'
```

⚠️ 其它探针里的 `page.screenshot({path:'.build/shots/x.png'})` 是**相对 cwd** 的，
从 `.build/` 跑会写到 `.build/.build/shots/`，于是量到的是几小时前的旧图、
**数值怎么改都不变**。我因此以为「改动没生效」，白查一轮。

## 五个已知根因

按出现频率排序，遇到反馈先按这个顺序查。

### ① 「塑料感」= 描边太重

物件被一圈深棕**完整封闭** → 读成剪下来贴上的贴纸。
用 `seam-check.mjs` 看**最外圈两像素的主色**：深棕（`70,44,29`）= 有粗描边，
浅色（`235,201,162`）= 已是同色系细线。

出图提示词绝不能写「深棕色描边」，改写：

```
不要用深棕色或黑色的粗描边把物体整个包起来：轮廓线要非常细、
并且用比该处填充色只深一到两档的同色系颜色
```

### ② 「割裂感」= 用描边色画了贯穿全屏的长线

墙地交界曾用 `COLOR.line`（深棕）画压条 → 一条深色横线把画面切成两半。
长线只能用「比相邻色深一点」的专用色。

另一半原因：**没有元素跨过墙地交界**。分区壁龛要下沉一点让地垫压在地板上
（实测竞品只越界 18px，不是整个壁龛坐到地上）。

### ③ 「像摆上去的」= 轮廓完整可见

首尾俱全的东西只能读成家具，画得再精细也改不了。
**被裁切 = 空间在画面外延续** —— 楼梯要推出屏幕右侧（溢出 62px、可见 72%），
壁龛顶部要伸出屏幕被 HUD 那条线裁断。

`check-overlap` 的 PASS **不够**：不重叠 ≠ 有溢出，用 `check-bleed.mjs`。

### ④ 「不舒服」= 饱和度偏高 + 明度偏低

反直觉：用户说「竞品饱和度更好」时，我们往往是**太艳太暗**。实测目标值：

| 指标 | 竞品 | 我们改前 | 目标 |
| --- | --- | --- | --- |
| 全图平均明度 | 95.2 | 89.7 | ≥ 91 |
| 全图平均饱和度 | 17.1 | 19.3 | 15~18 |
| 有彩色像素占比 | 9.8% | 15.5% | 10% 上下，**不超 12%** |
| 墙地明度差 | 7~9 | 5.9 | ≥ 6 |

两条容易搞反的关系：

- **墙要比地板更有颜色**（竞品墙 S21 / 地板 S10）。我们曾是墙 S7 / 地板 S22，
  关系完全反了 —— 地板比墙还黄，画面因此显得「闷」。
- **平铺花纹通道差留 10~14**。低于 8 等于没画（地板菱形格曾用 7/11/17，
  代码跑了但屏幕上一片纯色），高于 20 一整面墙读成塑料布。

**这一项极易过度修正。** 修「塑料感」时往灰里压确实有效，但压过头就变成
「灰扑扑、没层次」—— 曾把墙地明度差压到 **1.2**，墙和地几乎同色、画面糊成一片。
平衡点靠数值找，不要反复目测。

**彩色像素超标的典型原因**：图标全染成同一个主题色 → 一排单色剪影，
或者给每个图标配了色相但**纯度太高** → 画面吵。
正确做法是保住色相区分（功能可辨识的关键）、但每个色往浅里提一档。

### ④c 「UI 不够丰富」= 图标是单色剪影，要单独量按钮区

**全图统计会把这个问题藏起来。** 实测全图彩色占比已达标（9.2% vs 竞品 9.8%），
但用户仍觉得按钮单薄 —— 因为按钮只占屏幕一小块，被大片墙地稀释了。

用 `region-compare.mjs` 单独量：

```bash
node scripts/region-compare.mjs cmp/rival.png shots/now.png 0.78 0.76 1.0 0.94
```

实测右下角礼盒/挑战那块：

| 指标 | 竞品 | 我们（单色版） |
| --- | --- | --- |
| 彩色占比 | 27.8% | **5.4%** |
| **色相种类** | **8/12** | **1/12** |

底部图鉴/购置/领取：彩色占比 15.6% vs **1.2%**。

**「色相种类」是最灵敏的指标** —— 一个图标只用一个 `tint` 铺满时永远是 1/12。
竞品的礼盒一个就用了紫/粉/金/白多色。

修法：每个图标至少给 **3 个色相**、并且**明暗分层**（主色 + 暗部/浅部），
才有「立体图标」的观感。见 `ui/mapIcons.ts` 的 `ICON_*` 分件配色。

**换上真图之后还要查渲染尺寸。** 图标真图加载成功、`active=true`、frame 名正确，
量出来色相种类**仍然是 2/12** —— 因为渲染尺寸只给了 `ENTRY * 0.52`（约 29px），
多色细节被降采样吃掉了。放大到 0.74 才留得住。
**「加载成功」和「看得见」是两件事**，两个都要验。

### ④d 「简陋 / 没变化」= 轮廓对比不够，不是元素太少

用户说分区入口「简陋」、换了图还说「感觉没什么变化」时，**别去减元素**。
用 `edge-strength.mjs` 量相邻像素明度落差：

```
node scripts/edge-strength.mjs cmp/rival.png shots/now.png 0.02 0.07 0.30 0.22
```

实测洗浴间壁龛：

| 指标 | 竞品 | 我们 |
| --- | --- | --- |
| 明显轮廓占比（落差 >20） | **46.3%** | 22.8% |
| 强轮廓占比（落差 >50） | **26.5%** | 13.4% |
| 最深像素明度 | **91** | 59 |

**三个数必须一起读。** 我们有比竞品更深的颜色（59 < 91）却只有一半轮廓 →
深色全堆在一两块大面积暗部，而竞品把对比度**均匀分配到每个物件边界**。
结论：**竞品元素更多反而更清楚，靠的是边界对比而不是元素少。**
验收线「明显轮廓占比 ≥ 40%」，出图侧的提示词写法见 skill `game-art-from-ai`。

### ④e 肉眼确认要放大，别看原图

414×896 的截图里一个壁龛只有 116×135px，改动看不出来。
`crop-zoom.mjs` 把指定区域按整数倍最近邻放大（不插值，保留原始像素边界）：

```
node scripts/crop-zoom.mjs shots/now.png shots/zoom.png <x> <y> <w> <h> 6
```

把竞品同一部位也裁一份同倍数的，两张并排看才能定位差在哪。
**这一步省不掉** —— 我曾靠「色相种类 4/12 → 6/12」判断改动生效，
放大之后发现画面几乎没变。

⚠️ 放大之后仍然「没变化」时，**别继续调图** —— 先按 skill
`asset-change-verification` 查 `library/` 缓存是否已更新。
Cocos 不捕获脚本写入的文件，此时量到的是旧纹理，数字会稳定地骗你。

### ④b 采样点不可靠时看整图统计

`color-compare.mjs` 的「墙/地主色」是按固定相对坐标取样的，
换了布局就可能取到别的东西（我遇到过墙那块采样落在壁龛白瓷上，
报出墙 S7 而代码里实际是 S38）。

**整图统计（平均饱和度 / 平均明度 / 有彩色像素占比）不受采样位置影响，更可靠。**
两者矛盾时以整图统计为准，或者调 `region()` 的坐标重采。

### ⑤ 「入口太小」= 加宽没用，要加高

`placeArt` 等比缩放 `scale = min(框宽/图宽, 框高/图高)`。壁龛图是竖的，
**永远被高度卡住** —— 把框从 150 加宽到 194，图只从 75x80 变 80x86（大 7%），
玩家看不出任何变化，白改一轮。

用 `probe-artsize.mjs` 读**运行时渲染尺寸**判断有没有生效，
不要看分区框的尺寸（框大了图不一定大）。

要三个分区缩放一致，得把宽度给宽一点、让它们统一由**高度**限制；
否则各自限制点不同，缩出来是 26%/27%/30%，大小不齐。

实测尺寸参考（846 高的屏）：

| | 竞品 | 我们改前 | 我们改后 |
| --- | --- | --- | --- |
| 壁龛屏宽占比 | 27~32% | 21~26% | 26~28% |
| 壁龛屏高占比（含招牌） | 15~16% | **9%** | 17% |
| 图实际渲染 | ~125x155 | 75x80 | 160x171 |

### ⑥ 「割裂」还有一个结构性原因：没有元素跨过墙地交界

分区壁龛若完整待在墙裙之上，墙地之间**没有任何东西跨过去**，
上半屏和下半屏读成两张拼在一起的图。

竞品的洗浴间地垫、花园门垫、育婴室小地毯**都落在地板上**，
正是这些跨界元素把两半缝成一个房间。实测越界量只有 **18px**（屏高 2%）——
是「门槛伸出来一小截」，不是「整个壁龛坐到地板上」。

这个值容易两头都错：太大（80）整个壁龛被抬到交界线上方、悬在半空；
为 0 则一点不越界、读成全部镶嵌进墙。

## 墙占比：瓶颈常常不是墙

**占比必须按「屏幕顶」算，不能按「内容上沿」算。** 墙纸从屏幕顶端铺，
而内容上沿避让了 HUD。我曾用 `(top - wallBottom) / vh` 自查，一直显示
「26% 达标」，玩家看到的却是 **45%** —— 量截图量出 47% 才发现。

真正的约束是「分区壁龛 + 招牌必须塞进 HUD 下缘到墙地交界之间」。
HUD 吃掉 19% 时，23% 的墙只剩 31px 放壁龛（需要 110px），墙被迫留到 45%。
**减薄 HUD 才是前提**，四步压到 8%：

1. 头像 56 → 40
2. 等级徽章竖排 → 横排 → **压在头像下沿上**（overlap，不占额外高度）
3. 经验条 12px+数字 → 挂在货币条下方的 7px 细线
4. **左侧不避让微信胶囊**（省 40px）—— 胶囊固定在右上角，
   左上角的头像/货币条可以和它并排，竞品就是这样

## 改一处会连带三处

改墙高 → 地板变高 → **按 `floorH` 比例算的尺寸全部变大**。
`stairH = floorH * 0.95` 曾让楼梯长到 436x451、一件家具占半屏。
这类尺寸一律要有绝对上限（`Math.min(200, floorH * 0.62)`）。

分区加宽 → 墙缝变窄 → 挂件放不下。用 `wall-gaps.mjs` 算空档，别试。

**挪坐标挪到第三次就该算。** 「修好 A 撞到 B」的循环用 `free-space.mjs`
一次算清（实测后排想放五件需 380px、实际只有 368px，所以要移走一件）。

## 脚本清单

脚本随 skill 一起版本控制（`scripts/`）。**首次使用要先拷进 `.build/`**：

```powershell
Copy-Item .cursor\skills\ui-visual-parity\scripts\*.mjs .build\scripts\ -Force
```

依赖（`pngjs`、`playwright`）装在 `.build/node_modules`，而 ESM 按**脚本自身位置**
往上找 `node_modules` —— 直接从 `.cursor/skills/` 跑会报
`ERR_MODULE_NOT_FOUND`，**改 cwd 也没用**。所以必须拷过去、在 `.build/` 下跑。

| 脚本 | 用途 |
| --- | --- |
| `color-compare.mjs` | 两图配色对比：墙/地主色、明度差、饱和度、彩色占比 |
| `region-compare.mjs` | **只量指定区域**的饱和/明度/彩色占比/**色相种类** |
| `edge-strength.mjs` | 相邻像素明度落差 → **轮廓清脆度**，查「简陋 / 糊成一团」 |
| `crop-zoom.mjs` | 裁一块按整数倍最近邻放大，肉眼确认细节是否留得住 |
| `wall-ratio.mjs` | 扫饱和度跌变找墙地交界，算墙/地占屏比 |
| `seam-check.mjs` | 查外圈主色（描边）、四角 alpha（实心矩形）、填充率 |
| `shot-now.mjs` | 截图到**绝对路径**（避开相对路径坑） |
| `check-overlap.mjs` | 静态算道具/分区/楼梯重叠与挂件越界 |
| `check-bleed.mjs` | 校验楼梯溢出量与可见比例 |
| `check-hud.mjs` | 校验底部积分条放得下、顶部不越中线 |
| `wall-gaps.mjs` | 算分区之间的墙面空档，给挂件挑位置 |
| `free-space.mjs` | 算地板可用横向区间，判断放得下几件家具 |
| `floor-fill.mjs` | 地板按 x/y 分档，列出每档被谁覆盖 → 找空洞 |
| `probe-artsize.mjs` | 读运行时**图的渲染尺寸**（判断改动是否生效） |
| `probe-drag.mjs` | 拖前拖后对比 `WorldRoot.x`，验证横向可拖 |

改了 `mapLayout.ts` 的数值后，`check-overlap.mjs` / `wall-gaps.mjs` /
`free-space.mjs` / `floor-fill.mjs` 里的同名常量**要同步改**，否则查了个假的。

## 判断改动有没有生效

**看运行时的真实数值，不看截图。** 编辑器编译经常滞后甚至卡住：

```bash
# 源码 vs 产物时间戳
(Get-Item assets\scripts\ui\mapLayout.ts).LastWriteTime
Get-ChildItem temp\programming\packer-driver\targets\preview\chunks -Recurse -Filter *.js |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 LastWriteTime

# 产物里搜新常量，确认真的编进去了
Get-ChildItem temp\...\chunks -Recurse -Filter *.js | Select-String 'ZONE_SINK = 36' -List
```

⚠️ **产物里搜到新值也不够**：可能只有一部分 chunk 更新了。
最可靠的是 `probe-artsize.mjs` 读运行时的分区框尺寸。
本项目多次出现「产物含新常量、运行时仍是旧值」。

编译卡死超过 10 分钟：关闭 Cocos Creator → 删 `temp/`、`library/`、`build/`
→ 重开等导入。**不要删 `.meta`**（资源 UUID 在里面）。
